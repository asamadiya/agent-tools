ZFS burned a third of a fleet's CPU on machines that had no ZFS filesystem mounted

A microservice team doing metrics ingestion updated their base OS image and then reported that ZFS was eating over 30% of their CPU capacity. The engineer they asked for help had worked on ZFS internals at Sun and did not believe the claim, on the grounds that ZFS, unless it is badly misconfigured, does not have a code path that can burn that much CPU on a serving workload. He checked anyway, which is the only part of this story that everyone agrees was the right call, and the check turned out to confirm the symptom and demolish the diagnosis at the same time.

Atlas, the cloud-wide monitoring tool, showed 38% of CPU time in sys, which is not a normal number for Netflix cloud workloads. That is where a lot of investigations turn into an SSH session with mpstat(1) and perf(1) on one unlucky instance. Instead of that, he pulled a CPU flame graph through Netflix's fetch tooling (Vector at the time, FlameCommander later), which costs about as much operator time as reading a dashboard and gives you the whole stack rather than a per-CPU summary that tells you sys is high without telling you which sys.

The flame graph had two orange kernel towers. The left one was arc_reclaim_thread. The right one entered spl_kmem_cache_reap_now(), a second ZFS memory-freeing path, and the two towers being that wide at the same time is the shape you get when two threads are contending on the same locks, so the right tower was probably a consequence of the left one and not an independent problem. The ZFS Adaptive Replacement Cache (ARC) is the filesystem's main memory cache; arc_reclaim_thread runs arc_adjust() to evict buffers and hold a free-memory threshold, waking periodically or when the system reports memory pressure. The known historical cause of arc_reclaim_thread burning CPU is a tiny record size, say 512 bytes, which turns a working set into millions of buffers, but the default record size is 128 Kbytes and the usual advice is not to tune below 8 Kbytes, so that theory needed a misconfiguration nobody had made.

The first real theory was containers. A new infrastructure project was using ZFS as the container filesystem, and a host that churns containers churns filesystems, which would give ARC a genuine reason to reclaim constantly. The team said they were not using containers. Then they said they were not using ZFS at all.

They were right. df -h, mount, and zfs list on two instances showed no ZFS filesystems mounted, and /proc/spl/kstat/zfs/arcstats showed every counter at zero -- hits 0, misses 0, all of them. An ARC with zero hits and zero misses has never been asked to cache anything, and a cache that has never cached anything has nothing to evict, so arc_reclaim_thread should have had no work at all. At that point the flame graph and the kstats disagree, and the flame graph is the one holding a stack trace.

Reading the source and the change history resolved it. A performance feature had converted the ARC lists to multilists, one per CPU, to cut lock contention on eviction, and the eviction path picks which sublist to work on at random. The random choice went through the kernel's cryptographically-secure generator, which is why the flame graph paths ran down into get_random_bytes() and extract_entropy(). So the loop was: the ARC noticed low system memory on a busy instance, paid for a cryptographic random number to select a sublist, found the sublist empty because every sublist was empty, and repeated. The 38% sys was entropy extraction driven by memory pressure that had nothing to do with ZFS, on behalf of a cache holding nothing.

This was filed as ZFS issue #6531, and the first fix made arc_reclaim_thread bail out earlier when ZFS is unused, which removes this instance of the problem without touching the random selection that makes it expensive.

Two things are worth taking from this beyond the bug. The team's report was 30% and the measured number was 38% in sys, and both were correct measurements attached to a completely wrong cause, so the instinct to argue with the number was less useful here than the instinct to get a stack. And the counters that said zero were the evidence, not the contradiction: arcstats reading zero across the board is what told us the reclaim thread was spinning on an empty structure rather than doing expensive real work.
