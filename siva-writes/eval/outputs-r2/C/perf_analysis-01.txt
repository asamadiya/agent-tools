A 30% write latency regression from a distro upgrade, and the profile said it was the clock

We moved a Cassandra cluster from CentOS to Ubuntu as part of a fleet-wide migration in 2014, and write latency on the migrated instances went up by over 30%. Basic stats showed CPU consumption was also up by over 30%, which is the more useful of the two numbers: a latency regression on its own can live anywhere in the stack, including in places you have no instrumentation for, but a CPU regression that moves with it says the extra time is being burned on-CPU, on a machine we own, in a path a profiler can see. The instances are EC2 Xen guests, which constrains how we can profile them and which turns out to be part of the answer.

The first thing to rule out is that Ubuntu is simply running more things. top(1) showed only the Cassandra database consuming CPU -- no new daemon, no indexer, no monitoring agent that ships enabled on Ubuntu and disabled on CentOS. That leaves the case top(1) is structurally bad at, which is a churn of short-lived processes that are born and die between sampling intervals, so we ran execsnoop(8), the Ftrace-based version at the time, and it showed no such processes either. Whatever is eating the extra 30% is being eaten inside the Cassandra process.

We then collected CPU flame graphs on a CentOS instance and an Ubuntu instance in parallel. Running them at the same time is not a nicety here: this is a live cluster taking production traffic with a diurnal mix, and a profile collected on CentOS at 10am compared against a profile collected on Ubuntu at 2pm is partly a comparison of two different workloads. Collecting both at once makes the traffic mix a controlled variable rather than a confound.

The Java stacks were broken in both profiles, which is what you got before -XX:+PreserveFramePointer existed: the JVM uses the frame pointer register as a general purpose register, the frame pointer walk terminates almost immediately, and instead of a tower of Java methods you get one or two green frames sitting on top of whatever native code is underneath. That is normally a disaster for a profile, and here it was the thing that made the bug visible. Broken stacks merge call sites that would otherwise be distinguished by their callers, so the os::javaTimeMillis() calls, which in a correct profile scatter across dozens of thin stacks too narrow to notice, collapsed into a single block. That block was 30.14% of the middle of the Ubuntu flame graph, and searching the whole profile for the symbol brought it to 32.1%. The regression was 30%. Those numbers matching is suggestive rather than conclusive, but it is a good place to keep digging.

os::javaTimeMillis() calls gettimeofday(2), and underneath gettimeofday in the Ubuntu profile sat tracesys(), with syscall_trace_enter() and syscall_trace_exit() under that. Two theories fit. Theory A: syscall tracing is enabled on Ubuntu and not on CentOS, by auditing or apparmor or something else that installs a tracer, and every syscall now pays the trace entry and exit cost. Theory B: fetching the time is slower on Ubuntu for an unrelated reason -- a different libc path, a different kernel, a different clocksource -- and tracesys is incidental. The frame widths favor A: the trace frames are wide, and if the cost were in the timekeeping itself the width would sit in the clocksource read rather than in the enter and exit wrappers.

One caveat about the profile, which matters for how much weight the frame widths can carry. This is a Xen guest, so perf(1) is sampling with software cpu-clock soft interrupts rather than hardware NMIs. Software sampling cannot fire while interrupts are disabled, which means kernel paths that run with interrupts off are systematically underrepresented, and time the hypervisor spends on our behalf does not appear at all. The profile is a lower bound on kernel-side cost. It does not invalidate the comparison, since both profiles have the same blind spot, but any claim of the form "X is exactly 30.14% of CPU" should be read as "X is at least that, on the paths this sampler can see."

The Ubuntu profile also showed a vDSO frame with the syscall still above it, which reads as contradictory until you remember where this is running. The whole point of the vDSO is that gettimeofday returns without a syscall, by reading a shared page the kernel keeps current. Xen pvclock did not support the vDSO at that time, so the vDSO entry point is present, falls through, and issues the real syscall anyway -- which is what hands every time lookup to tracesys.

Two things are worth saying about the search itself. Colleagues who had done the same migration had not hit this, which is weak evidence that the trigger is specific to this workload or this instance configuration rather than to Ubuntu generally. And searching the internet for os::javaTimeMillis together with clocksource, tracesys, Ubuntu, EC2, or Xen returned nothing at all. For a bug in a database everybody runs, on an OS everybody runs, on the largest cloud in existence, that absence is itself informative: the combination that produces it is narrow, and almost nobody has a profiler pointed at it.
