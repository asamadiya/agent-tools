Twenty years of missing stack traces

If you have ever looked at a flame graph where a fat column of samples sits on the left edge, all of them bottoming out in libc with no application frames above, you have looked at the consequence of a compiler flag decision made in 2004 for a target that no longer exists in the form it had then. The %rbp register is the x86-64 ABI's frame pointer: it holds the base of the current stack frame, each frame stores the caller's %rbp, and an external profiler that does not have symbols, DWARF unwind tables, or any cooperation from the process can walk that chain and reconstruct the call stack. Linux perf does this. eBPF stack walkers do this. It is the cheap mechanism that makes whole-fleet profiling possible, and the ABI explicitly marks it optional -- code is free to index into its frame off %rsp instead, which removes two instructions from every non-leaf prologue and epilogue and hands one general-purpose register back to the register allocator.

On i386 that trade was clearly worth making, and Roger Sayle made it: he patched the gcc i386 backend so 32-bit targets compiled as though `-fomit-frame-pointer -ffixed-ebp` had been passed. i386 has eight architectural registers, of which four were realistically available to the allocator, so freeing %ebp took that pool from four to five, or from six to seven if you count %si and %di. That is a 25% increase in the thing that most directly determines how much a loop spills. Sayle gave two further reasons: he wanted to beat Intel's icc on benchmarks, which at the time gcc was losing, and he judged that debuggers of the era would be fine, since they already supported other ways of walking a stack.

The default then got carried across to x86-64, where every term of the argument is weaker. x86-64 has more than a dozen general-purpose registers before you free %rbp, so the increment is from sixteen to seventeen, roughly 6% against i386's 25%, and it lands in the regime where a compiler that is spilling is usually spilling for reasons a seventeenth register does not fix. Eric Schrock, then at Sun, objected to this in November 2004, and his objection is worth reading as a list of separable claims rather than as a single opinion. On amd64 a 17th register opens up no new class of compiler optimization, which is a stronger statement than "the win is small" -- it says the win does not change what the compiler can do, only how often it spills. What you actually avoid is a pushl/movl pair that the hardware has long since special-cased. Leaf routines never establish a frame at all, so the cost was never paid on the functions that are hottest by call count. Set against a permanent loss of debuggability, Schrock did not think the trade was worth making.

His closing line was the prediction that turned out to matter: the practice goes off the rails once people start compiling /usr/bin without frame pointers. Linux then did exactly that, and not only /usr/bin, but /usr/lib and application code too, which is the difference between an individual binary opting out and an entire platform opting out. When one binary omits frame pointers you lose that binary's frames. When libc omits them you lose everything above libc, because the walk terminates the moment it steps into a frameless function and cannot find the next link in the chain.

What this costs is not a uniform tax on all stacks; it is a selective erasure of exactly the stacks you were profiling to find. A walk that dies in libc returns a truncated trace, and truncated traces are indistinguishable from each other, so they merge into one tall column on the left edge of the flame graph -- 15% of samples in one example, 15% of your profile converted into a shape that tells you nothing. Off-CPU flame graphs come off worse, and for a structural reason: off-CPU time is, by construction, time spent in read, write, and mutex calls, which is to say time spent inside libc, which is to say the frames you lose are most of the population you are trying to measure.

The fix has taken two decades and has been done one runtime at a time. Java arrived at Netflix in 2014 with no frame pointer support at all, which broke every application stack, not just the libc-crossing ones; a c2 compiler fix written there was reworked by Oracle and shipped as `-XX:+PreserveFramePointer` in JDK8u60. libc came next, first as a locally built frame-pointer libc run in production, then as libc6-prof built with Canonical so that everyone else did not have to build their own. Each of those is a negotiation with a separate upstream, and each of them exists to undo a default that was set once, for a register pressure argument that was true on a four-register machine and was carried onto a sixteen-register one without being re-measured.
