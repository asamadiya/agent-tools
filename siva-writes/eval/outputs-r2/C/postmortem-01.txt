Root cause

A permissions change we deployed at 11:05 UTC on 18 November 2025 caused a routine internal query to return duplicate rows, which doubled the size of a configuration file that our proxy refuses to load past a fixed limit. The proxy then panicked and returned HTTP 5xx for a large share of traffic on our network. This was not an attack, and no data was lost or exfiltrated. It was our worst outage since 2019, and we are sorry.

The change itself was small and looked safe. It granted users on a ClickHouse database cluster visibility into metadata for the tables underlying the r0 database, rather than only the metadata for the default database they had been able to see before. Every query that reads system.columns runs with the caller's permissions, so after 11:05 those queries began seeing rows they had never seen.

Our Bot Management feature file is regenerated every five minutes by one such query. That query filtered on table name but not on database name, which was harmless while each user could see exactly one database and became wrong the moment they could see two. Each column now matched twice, once for the default database and once for r0, and the generated file carried more than double its usual number of feature rows.

The bots module in our proxy preallocates memory for that file and will not load more than 200 features from it. The bot-scoring model uses roughly 60 features at runtime, so the limit sat more than three times above anything production had ever produced and had never been approached in the file's history. The doubled file crossed it. In the FL2 path, written in Rust, the code that handles that condition returned an Err into an unwrap, and thread fl2_worker_thread panicked. A panicking proxy thread cannot serve the request, so the customer got a 5xx.

Two properties of the failure made it much harder to read than a normal bad deploy. First, the permissions change rolled out gradually across ClickHouse nodes, so for the next several hours a given five-minute regeneration might run against an updated node or an old one. Good and bad feature files alternated, and the network failed, recovered, and failed again on a five-minute cadence. A system that flaps that way looks far more like external pressure than like a configuration change, and when our independently hosted status page went down at the same time -- for reasons unrelated to this incident -- our responders' first hypothesis was an Aisuru-style DDoS against us and our status provider together. We spent time on that hypothesis that we should have spent on the feature file.

Second, the two proxy paths failed differently, and only one of them failed loudly. FL2 customers saw 5xx errors. FL1 customers saw no errors at all: the bot module fell through to a score of bot=0 for every request, so any customer with a rule that blocks on bot score began blocking real users, silently, with no error signal to indicate that anything was wrong. If you run such a rule and saw unexplained challenges or blocks in this window, that is the cause.

Impact began at 11:28. Automated monitoring fired the first alert at 11:31, three minutes later, and we opened an incident call at 11:35. At 13:05 we bypassed Workers KV and Access from the affected proxy path, which cleared the failures for those products. We stopped propagation of the bad feature file and pushed a known-good version at 14:24; core traffic was flowing normally by 14:30. We finished restoring the remaining services and declared all clear at 17:06.

The proximate bug is the unhandled Err, and we have already fixed it and the query's missing database filter. Neither is the interesting lesson. A configuration file generated by an internal system was consumed by our most critical path with the same trust we would give our own compiled code, and a limit meant as a safety bound became the trigger for a global failure because crossing it aborted instead of degrading. We are therefore hardening how the proxy ingests all internally generated configuration, eliminating the ability of a core dump or an error report to overwhelm system resources, reviewing every failure mode for error conditions across proxy modules, and adding global kill switches for features that consume such files.
