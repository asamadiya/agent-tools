Where to invest in agent tooling

The limit on what a coding agent can do is the quality of the feedback available to it, not the size of the model. An agent that can observe whether its last edit was correct will converge on a correct edit. An agent that cannot observe this will produce something plausible and stop. We propose funding the machinery that manufactures feedback, and treating model upgrades as something we consume rather than something we steer.

The evidence we have today already splits along this line. Agents stay unstuck where error messages are specific: a compiler that names the lifetime it cannot prove gives the agent an instruction, while a segfault gives it a mood. Rust is unusually productive for agents for exactly this reason, because it moves a class of incorrectness from runtime to compile time and reports it immediately. Agents do well on performance work wherever a benchmark exists, since the benchmark is a scalar the agent can hill-climb without asking anyone. Property-based testing outperforms its reputation here, because each generated counterexample is a fresh, precise, machine-readable statement of what is wrong. The failures run the other way. Architecture review is know-it-when-I-see-it, so an agent gets no signal until a human reads the diff. Concurrency is worse: the feedback for a data race is silent corruption discovered later, possibly in production, which is feedback with a latency measured in weeks.

Consider two projects that leadership would instinctively rank in the wrong order. The first is a delightful, ergonomic photo-editing website. The second is a correct, high-performance storage engine at the scale of RocksDB or InnoDB -- not a distributed database such as Aurora DSQL or PostgreSQL, just the engine. Ask a current open-loop model for a single shot at each and the website wins easily; it gets most of the way there and the storage engine does not compile. That ranking should invert as the loop closes. The website's feedback is a human deciding whether the crop handle feels right, and humans are slow, inconsistent, and expensive to interrupt, so every iteration costs a person. The storage engine has a specification: an API, a set of safety properties, and a set of liveness properties. All three can be checked by a machine at three in the morning. The agent can run that loop ten thousand times without asking us anything.

The investment follows from which loop we are trying to close. At compile time, fund the languages and libraries that make incorrectness explicit: Rust, Hydro for distributed dataflow, and Verus where we want proofs rather than tests. At modelling time, fund TLA+ and P so that concurrency and protocol bugs surface as a counterexample trace instead of as corruption. At specification time, fund spec analyzers of the kind Kiro ships, because a specification the agent can check itself against is the artifact that makes everything downstream automatable. And fund the unglamorous tier hardest: test harnesses, deterministic simulators, fault injectors, and mocks. That tier is where most of the feedback in our codebase would come from, and it is the tier that never gets staffed.

We are less certain about the timeline than about the direction, and the hypothesis is not yet falsified by anything we have measured. The check is cheap: pick one service, instrument how long an agent waits for a verdict on its own work, and drive that number down.
