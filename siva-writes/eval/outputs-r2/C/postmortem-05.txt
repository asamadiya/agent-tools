Remediation

On 20 February 2026, a cleanup sub-task passed pending_delete with no value, and roughly 1,100 BYOIP prefixes were withdrawn along with their service bindings. A single malformed call should not be able to do that, and recovery from it should not require a database snapshot. We are running three workstreams to close both gaps, plus a fourth item that already governs them.

We are standardizing our internal API schemas so that a call like this one is rejected before it executes. pending_delete was passed as an untyped string. Neither the client nor the server could reason about its value, so an empty string travelled the same path a legitimate identifier would have, and the deletion proceeded on the empty match. A stricter schema gives both ends something to validate against: tooling can check whether a call is well formed, and a call that is not well formed fails at the boundary rather than in the database.

We are separating operational state from configured state. Today, customer configuration and operational actions write to the same authoritative database, which is why recovery meant restoring from database snapshots instead of reconciling desired state against actual state. The replacement is a snapshot of what is read from that database and applied to production, rolled out the way we ship binaries: staged, gated by health metrics that halt a bad rollout, and revertible. That gives us near-instant revert of an individual customer or of all customers to a known-good version. The tradeoff is real and we want customers to see it stated plainly. While a snapshot is held during an outage, direct API updates to configuration are temporarily blocked. Traffic keeps being served. We think blocked configuration changes for the duration of an incident are the better outcome than prefixes going down, and this incident is the evidence.

We are adding a circuit breaker on the rate and breadth of change. Monitoring will flag an unusual volume of BGP prefix withdrawals or deletions -- a burst on the scale of the 1,100 prefixes withdrawn here is exactly the signal -- and halt snapshot deployment when it fires. Signals from direct monitoring of customer services can trip the same breaker, so the halt does not depend only on us correctly instrumenting the control plane that failed.

Recovery was uneven across affected customers, and the reason is worth recording because it shapes what we build next. Prefixes that were only withdrawn came back with a dashboard toggle. Prefixes that were withdrawn and had some of their service bindings removed were partially recoverable, with the remaining bindings needing manual restoration. Prefixes that lost all of their bindings required a global configuration push to every edge machine, which is the slowest path we have. The three classes differ only in how much state was destroyed before the sub-task stopped, which is another way of saying the blast radius of one bad call determined the recovery time for each customer.

All of this sits under Code Orange: Fail Small, the company-wide effort we started after the November 2025 incident. Its three buckets are controlled rollouts for any configuration change that propagates across the network, break-glass procedures that carry no circular dependencies on the systems they recover, and well-defined behaviour under all failure modes rather than behaviour defined only for the modes we anticipated. The schema work, the snapshot rollout, and the circuit breaker land in the first and third buckets. We will report progress on them alongside the rest of Code Orange.
