Cloudflare Dashboard and API outage, 12 September 2025

All times UTC.

Summary

The Cloudflare Dashboard and much of the public API returned 5xx errors for 75 minutes, from 17:57 to 19:12 on 12 September 2025. The cause was a bug we shipped in the Dashboard at 16:32 that turned a single page load into a flood of API calls, which overwhelmed the Tenant Service that authorizes every API request. We are sorry. If you were trying to change configuration during that window, your changes failed, and that is our fault.

Traffic through our network was not affected. The control plane and the data plane are strictly separated, so proxying, DNS, WAF and the rest of our network services kept running throughout. Most customers noticed nothing unless they opened the Dashboard or called the API.

What happened

Tenant Service sits in the authorization path for API requests. It is a Go process running on Kubernetes in a subset of our datacenters, and when it cannot evaluate whether a request is authorized, the request returns a 5xx rather than being let through. That makes its available capacity a hard ceiling on Dashboard and API availability.

The Dashboard release at 16:32 called the /organizations endpoint from a React useEffect whose dependency array held an object that was reconstructed on every state or prop change. React compares those dependencies by identity, so a freshly constructed object is always unequal to the previous one, and the effect re-ran on every render. One user loading one page produced many calls per render, and each failure was retried, which produced more calls. The Dashboard absorbed this without visible symptoms for 85 minutes because Tenant Service still had headroom.

At 17:50 we deployed a new version of Tenant API Service. Seven minutes later Tenant Service was overwhelmed and Dashboard availability began dropping. We added pods and applied a global rate limit, and by 18:17 the API had recovered to 98% availability. The Dashboard did not recover with it: restarting Tenant Service forced every open Dashboard session to re-authenticate at once, and the retry loop in the buggy client turned that thundering herd into a sustained one.

At 18:58 we shipped a change intended to remove the erroring codepaths. It made API impact worse. We published a temporary rate-limiting rule at 19:01, then reverted both changes at 19:12, and Dashboard availability returned to 100%.

Two things made this harder to diagnose than it should have been. Our telemetry could not distinguish a retry from a new request, so the request-rate graphs told us load was high without telling us that a single client was generating most of it. And Argo Rollouts, which watches error rates during a deploy and rolls back automatically, had not yet been adopted for Tenant Service. Had it been, the 17:50 deploy would have been reverted without a human in the loop.

What we are changing

We are hardening the Dashboard's API calls so a client-side bug cannot produce unbounded request volume: dependency-stability checks in review, and client-side rate limiting behind the API layer.

We are completing the Argo Rollouts migration for Tenant Service so that a deploy that raises error rates is rolled back automatically.

We are adding retry and attempt metadata to our request telemetry so responders can separate new requests from retries during an incident.

We are provisioning Tenant Service so that it can absorb the re-authentication load generated by a restart, instead of depending on clients to back off.
