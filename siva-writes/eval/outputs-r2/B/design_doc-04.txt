Architecture: a disaggregated data service

What the service takes off the caller

The service should remove scale, reliability, durability, and multi-region fault tolerance from what an application builder thinks about. Aurora DSQL states that goal directly: a database of first resort, simple to adopt at low scale, growing with the application without adding complexity. We take the same bar. A team that starts on us at 10 requests per second should not have to migrate off at 10,000, and should not have to learn a second operational model in between.

Agents raise the value of that bar. A coding agent writes good code and is weak at long-horizon tasks, and database operations -- capacity planning, failover drills, version upgrades, index maintenance -- are long-horizon work. Every concern the service absorbs is a concern an agent cannot abandon halfway through.

Decomposition

Split the system into independent services, each owning a small number of well-defined concerns. This is not new: Aurora and DynamoDB disaggregated OLTP before DSQL did. Our departure point is DSQL's, which is to separate replication from transaction isolation and both of those from storage. The isolation layer decides commit order. The replication layer decides durability and placement. The storage layer owns bytes on local SSD. Each of the three scales, deploys, and rolls back on its own schedule.

Three lessons carry over from running the earlier systems at scale.

Avoid large caches. A large cache makes failover slow, because the replacement node serves cold traffic until its working set refills, and it makes read scaling awkward, because every reader added pays the same warm-up. Size caches so a cold node is slower and still correct, never unavailable. Measure the cold-start penalty and publish it as a number in the runbook.

Offer strongly consistent scalable reads. Reads that are both linearizable and horizontally scalable delete whole classes of problem: hot keys stop needing special handling, and callers stop partitioning their data to route reads at particular replicas. The alternative is pushing consistency into every caller, which is the opposite of a database of first resort.

Push expensive operations down into storage. Run scans, filters, and aggregates next to the local SSD. Moving a predicate to storage moves its selectivity with it, so a scan that returns 1% of rows ships 1% of the bytes across the network instead of all of them.

Multi-tenant packing

Pack many tenants onto a physical machine, because the peak-to-average load ratio on that machine falls at approximately sqrt(N) for N loads. The Firecracker paper makes the same argument. This matters because cost scales with provisioned peak while revenue scales with average consumption: at 100 tenants the ratio improves roughly 10x, and the gap between the two curves is the margin.

The sqrt(N) result assumes the loads are independent. Tenants sharing a diurnal cycle, a region, or an incident are not independent, and correlated peaks collapse the benefit. Instrument realized peak-to-average per fleet and compare it against sqrt(N) rather than assuming the model holds. If a fleet's measured ratio sits well above the prediction, the packing policy is grouping correlated tenants and should be changed.
