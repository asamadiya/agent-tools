Cassandra got 30% slower when we moved it to Ubuntu

In 2014 we were migrating services from CentOS Linux to Ubuntu. One Cassandra cluster made the move and write latency went up by over 30%. Basic stats put CPU consumption up by over 30% as well, which is the useful half of that pair: latency can climb for a dozen reasons, but a CPU number that moves with it says the extra time is being burned on-instance, not waited on. Same application, same EC2 Xen guests, different distribution.

top(1) was the first thing to check, and it came back boring. The Cassandra database was the only process consuming CPU. No Ubuntu service had shipped along with the new base image and started eating a third of the box in the background. That is the cheap explanation and it was dead.

The next cheap explanation is a process too short-lived for top(1) to sample. execsnoop(8), the Ftrace version at the time, traces execs as they happen and catches a process that lives for eight milliseconds. It showed nothing. Whatever was consuming the extra CPU was inside the Cassandra process itself.

So we collected CPU flame graphs, one on a CentOS instance and one on an Ubuntu instance, running at the same wall-clock time. That parallel collection matters more than it sounds. Cassandra's traffic mix changes through the day, and a CentOS profile from Tuesday morning compared against an Ubuntu profile from Tuesday evening is a comparison of two workloads that happen to share a hostname prefix.

Both flame graphs had broken Java stacks. This was before -XX:+PreserveFramePointer existed, so the JVM's omitted frame pointers left perf(1) unable to walk the Java portion of the stack: one or two green frames where a tower of Java methods should be. The breakage turned out to be useful. With the Java frames collapsed, every call site that reached os::javaTimeMillis() merged into a single block instead of scattering into dozens of thin stacks that no eye would group together. Working stacks would have hidden this cost by spreading it.

That block was 30.14% of the Ubuntu flame graph, sitting in the middle, and searching the graph for the same function summed it to 32.1% of samples. Cassandra timestamps writes, so it calls System.currentTimeMillis() constantly; the JVM implements that as os::javaTimeMillis(), which calls gettimeofday(2). A third of the CPU on the box was being spent asking the kernel what time it was.

Above gettimeofday(2) on Ubuntu the stack continued into tracesys() and syscall_trace_enter/exit(). Those frames give two theories. Theory A: syscall tracing is enabled on Ubuntu and is not on CentOS, auditing or apparmor being the obvious candidates. Theory B: fetching the time is simply slower on Ubuntu, through a different library path or a kernel and clocksource change, and the tracing frames are incidental. The frame widths favored A, since the tracing frames carried measurable width of their own instead of appearing as a thin garnish on an otherwise identical call path.

One caveat belongs in the record before anyone treats those percentages as exact. This is a Xen guest, so perf(1) was profiling with software cpu-clock soft interrupts and not hardware NMI. Software sampling cannot fire in kernel paths that run with interrupts disabled, and all hypervisor time is invisible to it. The profile is therefore biased toward code that is interruptible, and 32.1% is a floor on the time-fetching cost with an unknown correction on top, not a measured total.

The Ubuntu graph also showed a vDSO frame with the syscall still above it, which is the detail that explains why this cost exists at all. gettimeofday(2) is supposed to be serviced in userspace through the vDSO and never reach the kernel. Xen pvclock did not support vDSO at the time, so the fast path was entered and fell through into a real syscall, and that syscall then paid whatever the tracing path charges. Two independent conditions had to be true for a third of the CPU to disappear here: a clocksource with no vDSO implementation, and a syscall entry path doing extra work.

Nobody had a prior on this. Colleagues running the same migration had not hit it, and searching for os::javaTimeMillis alongside clocksource, tracesys, Ubuntu, EC2 and Xen returned nothing on the internet. That absence is worth stating plainly because it is the normal case for a performance problem that lives at the intersection of four components, none of which is broken on its own.

If you are carrying a JVM workload across a distribution boundary on Xen, measure this directly. Run a loop calling System.currentTimeMillis() and time it on both images. Check the clocksource in /sys/devices/system/clocksource and confirm whether gettimeofday(2) reaches the kernel by counting syscalls under strace or a tracepoint. Then check whether syscall tracing is on. Three minutes of that would have found the 32.1%.
