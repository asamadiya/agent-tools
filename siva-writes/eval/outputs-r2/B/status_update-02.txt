Status: search-federator 2026.9.3 canary is over SLO. Revert decided Sep 15, re-canary Sep 22.

The canary build has been running on 4 of 240 production hosts since Sep 8 and it misses the service's p99 latency SLO. Canary hosts serve p99 at 311 ms against 184 ms on the control fleet, an increase of 127 ms or 69%. The SLO is p99 under 250 ms; the canary sits 61 ms over that line. p50 is essentially flat, 41 ms on control to 42 ms on canary. Dan Ortiz owns the build and took the decision described below.

The error budget is untouched. The canary carries 1.7% of traffic, matching its 4-of-240 host share, and it has consumed zero error budget to date. The finding is not that members are being hurt now. The finding is that promoting 2026.9.3 to all 240 hosts would take the whole fleet over SLO.

A new gRPC interceptor causes the regression. It validates every response payload against a JSON schema on the serving path, synchronously, before the response leaves the host. Compiling a schema is the expensive step, and compiled schemas live in a 512-entry LRU cache. The interceptor costs 0.9 ms at the median and 94 ms at p99, and that p99 figure is schema recompilation, not the validation walk itself.

The cache is too small for the live working set. Canary hosts touch roughly 3,400 distinct schemas at 2,900 QPS per host, which leaves a 512-entry LRU covering about 15% of the working set. Measured hit rate on canary is 71%. That 29% miss rate explains the shape of the change precisely: misses are rare enough that the median request never pays a recompile, and common enough that a request in the slowest 1% almost certainly does. At 2,900 QPS, a 29% miss rate is roughly 840 recompilations per host per second.

The pre-release load test missed this because it exercised 300 schemas. Three hundred entries fit inside a 512-entry cache with room to spare, the test measured a 99.6% hit rate, and the interceptor cost it observed sat near the 0.9 ms median. The test was accurate about the code it ran and wrong about the input distribution it ran against. Compare 300 schemas to the 3,400 we actually see: the test never left the cache-resident regime that production spends 29% of its requests outside of.

We took three actions on Sep 15. Revert the interceptor from the release branch, so 2026.9.3 ships without it. Raise the schema cache from 512 to 8,192 entries, which holds the current 3,400-schema working set with about 2.4x headroom for growth. Move validation behind a sampling flag set at 1%, so the serving path pays the recompilation tail on one request in a hundred instead of on 29 in a hundred. Re-canary is scheduled for Sep 22.

We are asking SLO owners for two things before Sep 22. First, confirm that 1% sampled validation is acceptable coverage for the payload-correctness goal the interceptor was written for; if it is not, we need a different design, because full synchronous validation on the serving path does not fit inside a 250 ms p99 budget at this schema cardinality. Second, hold us to a gate on the re-canary: cache hit rate above 99% and canary p99 within 10 ms of control, both measured over 24 hours at production schema cardinality rather than at load-test cardinality.
