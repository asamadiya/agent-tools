Root cause

At 11:05 UTC on 18 November 2025 we deployed a permissions change to a ClickHouse database cluster. The change let users read metadata for the tables underlying the r0 database, not only the tables exposed through the default database, and on its own terms it did what we intended. One consumer of that metadata had been written against the narrower permissions: the query that builds the Bot Management feature file. All times below are UTC.

That file is regenerated every five minutes by a query over system.columns. The query filters on table name and does not filter on database name. Before 11:05 each column appeared once in the result set, because the account running the query could see only the default database. After 11:05 the same column appeared twice -- once for default, once for r0 -- and the generated file carried more than double the feature rows it had carried for years. Neither the query nor the file format treated a duplicated row as an error.

The proxy's bots module preallocates memory for that file and will not load more than 200 features from it. The bot-scoring model uses about 60 features at runtime, so the limit sat more than three times above the working set and nothing had approached it. The doubled file crossed it. On the FL2 Rust path the load returned an Err, the calling code unwrapped it, the thread named fl2_worker_thread panicked, and every request that thread was handling returned HTTP 5xx. The limit did what it was written to do. The code around it treated "more than 200 features" as a state that could not occur instead of as an input it had to reject.

Our two proxy generations failed in different ways, which made the reports reaching the incident call contradict each other. Customers on FL2 saw 5xx. Customers still on FL1 saw no errors at all, and instead received a bot score of 0 on every request. Anyone running a rule that blocks on bot score therefore blocked legitimate traffic, with clean error rates and no signal that anything had changed. Those two symptom sets arrived at the same time from the same underlying file.

The permissions change rolled out gradually across ClickHouse nodes, and this shaped the next three hours more than any other single factor. Whether a given five-minute regeneration produced a good file or a bad one depended on which node answered the query, so the network broke, recovered, and broke again on a five-minute cadence. Each recovery was evidence against a bad deploy and against a bad config push, which are the two hypotheses an oscillating failure most resembles and the two we could rule in or out fastest.

Cloudflare's status page is hosted outside our infrastructure and shares no component with the network. It went down inside the same window for reasons unconnected to this incident. Read together with an oscillating global failure, that coincidence pointed at a large-scale attack against both the data plane and our ability to communicate about it, and responders spent early minutes of the call working an Aisuru-style DDoS hypothesis. We were wrong about that, and no attack of any kind contributed to this outage.

Impact began at 11:28. Automated detection fired at 11:31, three minutes later, and we opened an incident call at 11:35. At 13:05 we bypassed the affected path for Workers KV and Access, which restored those products ahead of the rest. At 14:24 we stopped propagation of the bad feature file and began pushing a known-good copy. Core traffic was normal at 14:30, two hours and two minutes after impact started, and we declared all clear at 17:06 once downstream services had drained their backlogs.

Stated once and plainly: a query trusted the shape of its own permissions and returned each row twice when those permissions widened; a limit chosen with three times' headroom over the model's real appetite became reachable the moment its input doubled; and an unwrap converted a bounded, recoverable condition into a panic inside the request path. This is the worst Cloudflare outage since 2019, and we caused all of it ourselves.
