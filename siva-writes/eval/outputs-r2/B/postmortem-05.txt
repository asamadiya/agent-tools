Remediation

A cleanup sub-task passed pending_delete with no value, the API accepted the call, and roughly 1,100 BYOIP prefixes and their service bindings were deleted. Three workstreams follow from that failure: a stricter API schema, separation of operational state from configured state, and a circuit breaker on the rate and breadth of change. All three sit under Code Orange: Fail Small.

Recovery cost varied by how far each deletion got, and the spread shapes the plan. Prefixes that were only withdrawn came back with a dashboard toggle. Prefixes withdrawn with some bindings removed recovered partially, leaving engineers to rebuild the missing bindings by hand. Prefixes withdrawn with every binding removed needed a global configuration push to every edge machine, which is the slowest repair path we have. The same single malformed call produced all three classes, so the fixes below target the call, the state it mutates, and the blast radius it can reach.

API schema standardization. The value pending_delete travelled as an untyped string, which left neither the client nor the server able to reason about it: an empty value looked like a legitimate value. We are moving these fields to a stricter schema with enumerated values and a required non-empty constraint. Tooling can then validate whether a call is well formed before it reaches the authoritative database, and a sub-task that omits the field fails at the boundary instead of matching every row.

Separating operational state from configured state. Customer configuration and operational actions write to the same authoritative database today. When that database is wrong, engineers restore from database snapshots, because there is no separate record of what production was actually running to reconcile against. We will snapshot what the service reads from the database and applies to production, then roll those snapshots out the way we ship binaries: staged across the fleet, gated by health metrics that halt a bad rollout before it reaches the next stage. Reverting a single customer or all customers to a known-good version becomes near-instant, measured in the time to propagate one snapshot instead of the time to restore and replay a database.

This design carries a real tradeoff, and we are choosing it deliberately. While a rollout is halted, customers are temporarily blocked from applying updates through the API directly. In exchange, their traffic keeps being served from the last known-good snapshot instead of going down. We would rather delay a configuration change by minutes than withdraw a prefix.

Circuit breaker. The third workstream adds monitoring that flags an unusual rate or breadth of change and halts snapshot deployment on its own. A burst of BGP prefix withdrawals or a deletion count far outside the normal band for that window trips it. Signals from direct monitoring of customer services feed the same breaker, so a drop in reachability observed from outside can stop a deployment that internal metrics still call healthy.

Code Orange: Fail Small collects these into three buckets, and each workstream lands in one. Controlled rollouts for any network-propagated configuration change: the snapshot pipeline with health gating. Break-glass procedures without circular dependencies: recovery paths that do not depend on the control plane they are recovering. Well-defined behaviour under all failure modes: the schema work, which turns an ambiguous empty string into a rejected request. We will report progress against each bucket, and the first measure we owe you is the time to revert a single customer, which is minutes today and should be seconds.
