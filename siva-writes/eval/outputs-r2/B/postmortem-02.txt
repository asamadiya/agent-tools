Impact analysis

This section covers what the 18 November 2025 incident did to the services enterprise customers consume. It does not cover the core proxy failure itself. All times are UTC.

Workers KV returned heavily elevated 5xx for most of the window. The KV front-end gateway resolves reads and writes through the core proxy, and the core proxy was failing, so every KV operation inherited that failure. At 13:04 we shipped a patch that let the KV gateway bypass the core proxy entirely. Error rates fell immediately for KV and for everything that sits downstream of it, which includes Access and the Dashboard. If your Worker reads configuration, session state, or feature data from KV, assume those reads failed between the start of the incident and 13:04 unless you cached them at the edge.

Cloudflare Access failed authentication requests from the start of the incident until the rollback at 13:05. The failure mode was contained in one respect that matters for audit: every failed authentication terminated at an error page, so no user reached a protected application while authentication was broken. Logins that did succeed during the window were logged correctly, and existing Access sessions continued to work throughout -- users already holding a session saw nothing. Access configuration changes attempted during the window are the residual risk. Some failed outright and some propagated very slowly. We have since recovered all of them, but if you pushed a policy change between the start of the incident and 13:05, confirm the live policy matches what you intended.

Dashboard availability dropped across two separate windows, and the second one had a different cause from the first. The first ran 11:30 to 13:10. The Dashboard reads from Workers KV internally and calls Turnstile in the login flow; Turnstile failed to load, so anyone without an active session could not log in at all. That window closed at 13:10 as the KV bypass took effect. The second ran 14:40 to 15:30. Restoring the feature file released a backlog of queued login attempts, and client retries piled on top of the backlog, which exceeded control plane capacity. We scaled control plane concurrency around 15:30 and availability recovered. API traffic authenticated by token was not subject to the Turnstile failure.

Email Security kept processing and delivering mail for the full duration. No message was dropped. The degradation was in detection quality: the service lost access to one IP reputation source, which reduced spam-detection accuracy and suppressed some detections that depend on domain age. Some Auto Move actions failed to execute. We have remediated those actions. Messages delivered during the window carry a higher false-negative rate than normal, so treat that period's inbox as less filtered than usual.

CDN response latency rose across the window for a reason unrelated to KV. Our debugging and observability systems enrich uncaught errors with stack and request context, and the error volume drove those systems to consume large amounts of CPU on the same machines serving customer traffic. Cache hits and origin fetches still completed; they completed slower. Customers with tight client-side timeouts on Cloudflare-fronted origins may see this recorded as timeout errors rather than as latency.

Two things are worth stating plainly. Traffic served entirely from cache, without a KV read or an Access check, was affected only by the added latency. And the remediation for KV at 13:04 is what resolved the majority of the customer-visible blast radius.
