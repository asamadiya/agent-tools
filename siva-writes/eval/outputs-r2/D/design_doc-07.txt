How to reason about coding-agent capability

A coding agent is a feedback loop built around an LLM, and what the agent can deliver is set by the error signal circulating in that loop far more than by the open-loop quality of the model inside it. This is the frame we should use when we plan tooling work, and it points our budget somewhere other than the next model release.

An opamp and an analog multiplier IC make the argument concrete. Wire an MC1495 -- a multiplier part that has been obsolete for years and that nobody would call precise -- into the feedback path of an opamp. Apply a voltage on the left and the output on the right is its square root. The opamp computes no square root. It drives its two inputs toward equality, and because the output is routed back through the multiplier as output times output, equality holds only where the output squared equals the input. The precision of the answer comes from the comparison and the loop gain, not from the multiplier.

Components inside a feedback loop behave very differently from the same components measured open-loop. That is the general statement of the circuit, and its practical consequence is that excellent outputs can be extracted from poor components if the loop around them closes on a sharp comparison. The comparison is what has to be good.

An LLM is the multiplier in our loop. Its open-loop behavior is useful and flawed, in the way an analog part is useful and flawed, and nothing in the frame requires that to change. The comparison is supplied by the compiler, the type checker, the test suite, the linter, and the program actually running against a fixture. Developer tooling moved over roughly two years from open-loop autocomplete in the IDE, where the human closed every loop by reading a suggestion, to agents, which relocated the build-test-iterate loop inside the agent itself. The loop did not appear in those two years. It changed owner.

Computers have been super-human at some tasks for at least 85 years, dating to Marian Rejewski's work in the 1930s, and the shape of that capability has not changed since. A current MacBook adds 64-bit numbers roughly 100,000,000,000 times faster than a person does. Across the same nine decades, computers remain well short of a person on other tasks that a person finds easy. Expect coding agents to land in that same uneven shape: super-human where the loop closes on a machine-checkable comparison, and short of a good engineer where no such comparison exists.

We should therefore fund the error signal, and rank the work by how sharp and how fast the signal is. A test suite that fails in 30 seconds and names the failing assertion is a higher-gain comparison than one that fails in 20 minutes with a stack trace. Typed interfaces, hermetic builds, runnable repros, and deterministic fixtures are all loop-gain investments, and they pay off for human engineers on the same mechanism. Where we cannot build a machine-checkable comparison -- is this API pleasant, is this abstraction the right one, is this the product we should ship -- the loop stays open and a human stays in it. Name those cases explicitly in any agent proposal, because they are where the capability argument stops applying.
