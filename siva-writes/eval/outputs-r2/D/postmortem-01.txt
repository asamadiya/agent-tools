Root cause: a permissions change doubled a configuration file past a 200-feature limit

A database permissions change made an internal query return duplicate rows, which more than doubled a Bot Management configuration file, pushed it past a hard limit of 200 features in our proxy, and caused the proxy thread that read it to panic and return HTTP 5xx. No attack was involved. We initially believed one was, and we explain below why the failure signature misled us.

The file that broke is regenerated every five minutes by a query over ClickHouse's system.columns, and that query filtered on table name without filtering on database name. At 11:05 UTC on 18 November we deployed a permissions change to the ClickHouse cluster granting users visibility into metadata for the underlying tables in the r0 database, not only the tables in default. The same columns then matched twice, once per database. Every regeneration after 11:05 produced a feature file with more than twice the rows it had carried that morning.

Our proxy refuses to load more than 200 features from that file. The bots module preallocates memory for the file, and 200 was picked as a bound well above the roughly 60 features the bot-scoring model evaluates at request time. That is more than three times headroom, and in the years the limit has existed, production had never come close to it. The doubled file carried more than 200 features on the first regeneration after the permissions change.

Crossing the limit reached an unwrap on an Err value in the FL2 Rust path, which panicked: thread fl2_worker_thread panicked. A panic in that thread cannot be recovered into a served response, and every request routed through an affected proxy returned 5xx. The limit was written as a safety bound and the code enforcing it treated exceeding it as impossible, not as an input to be handled, which is what turned a bad config file into a full traffic failure.

Customers saw two different failures depending on which proxy engine served them. FL2 customers received 5xx on affected requests. FL1 customers received no errors at all and instead got a bot score of 0 on all traffic, which meant any customer rule blocking on bot score produced false positives against legitimate users. The second failure is quieter and, for customers running block rules, was not less damaging.

The network recovered and failed again repeatedly for roughly three hours, because the ClickHouse permissions change rolled out gradually across nodes. Each five-minute regeneration ran against whichever node it landed on, and the query returned duplicate rows only from nodes that had already received the change. Good and bad files therefore alternated on a five-minute cadence, each one propagating to the edge and replacing its predecessor. That oscillation is the reason we suspected an Aisuru-class DDoS first: an internal bad deploy does not usually heal itself and re-break on a fixed interval, and an attack that ramps and backs off does. Our status page, which is hosted entirely outside our infrastructure and shares no dependency with it, went down at the same time by coincidence, which reinforced the wrong hypothesis.

The timeline, all times UTC. 11:05 permissions change deployed. 11:28 customer-facing impact begins. 11:31 first automated detection. 11:35 incident call opened. 13:05 Workers KV and Access bypassed the affected proxy path, removing impact for those products. 14:24 we stopped propagation of new feature files and pushed a known-good file. 14:30 core traffic flowing normally. 17:06 all downstream services recovered and the incident closed. This was our worst outage since 2019.

The decision this forces is that we stop treating files we generate ourselves as trusted input. Configuration produced by our own pipelines passes through no row-count or schema check before it propagates, while configuration a customer submits through the API is checked against both. We control both ends of a five-minute query whose result set changed because of an unrelated permissions grant on a different system. Three changes follow from that. We are adding validation of generated feature files against expected row counts and schema before they propagate; a file that doubles in size is rejected at generation, before any proxy reads it. We are removing the ability of any module reading a configuration file to panic the request path, with the failure mode being a stale-but-valid file and a paged alert. We are adding global kill switches for individual proxy features; a misbehaving module can then be taken out of the request path in seconds, not in the three hours this one took.
