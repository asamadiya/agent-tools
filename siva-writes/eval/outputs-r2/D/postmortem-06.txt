Cloudflare Dashboard and API outage, 12 September 2025

The Cloudflare Dashboard and much of the public API returned 5xx errors for 75 minutes on 12 September 2025, from 17:57 to 19:12 UTC, because a bug in the Dashboard sent repeated calls to an endpoint served by Tenant Service, and Tenant Service authorizes every public API request. We are sorry. If you tried to change a configuration during that window, the change most likely failed.

Only the control plane failed. Cloudflare keeps the control plane and the data plane strictly separated, and no network service -- proxying, DNS, WAF, Workers -- depended on Tenant Service during the incident. Customers who were serving traffic and not making configuration changes saw nothing.

The Dashboard generated the load through a React useEffect hook whose dependency array held an object that was recreated on every state or prop change. React compares dependencies by identity, saw a new object each render, and re-ran the effect, which issued another call to /organizations. Failed calls retried, retries changed state, and state changes triggered fresh renders. The request rate therefore scaled with the number of open dashboard tabs and with the error rate itself, not with anything a user chose to do.

Tenant Service converts that load into a full API outage because it sits in the authorization path. Every public API request asks Tenant Service whether the caller may act on the tenant, and a request whose authorization cannot be evaluated returns 5xx instead of proceeding unauthorized. The Dashboard is itself a client of that API. A saturated Tenant Service therefore broke the Dashboard and was fed by it at the same time.

The buggy Dashboard version shipped at 16:32 and did not take anything down on its own. At 17:50 a new Tenant API Service version deployed, and at 17:57 Tenant Service was overwhelmed and Dashboard availability began dropping. Responders added pods to the Go service, which runs on Kubernetes in a subset of our datacenters, and applied a global rate limit; by 18:17 the API had recovered to 98% availability, while the Dashboard had not recovered at all. A change at 18:58 meant to remove erroring codepaths made API impact worse. A temporary rate-limiting rule went out at 19:01, we reverted the 18:58 changes at 19:12, and Dashboard availability returned to 100%.

Restarting Tenant Service was itself a source of load, because every open dashboard re-authenticated at the same moment and the render loop multiplied that herd. This is why adding capacity moved API availability to 98% at 18:17 without moving the Dashboard: the clients that were failing were the same clients generating the traffic, and each recovery attempt handed them a fresh synchronized start.

Two specific gaps extended the incident, and both are being closed. Tenant Service had not yet adopted Argo Rollouts, which automatically rolls back a deployment on detected errors and would have reverted the 18:58 change without a human deciding to; we are onboarding Tenant Service to Argo Rollouts. Responders also could not tell retries from new requests in Tenant Service telemetry, which left the size and shape of the amplification invisible for most of the 75 minutes; we are labelling retried requests at the client and exposing that dimension in our dashboards.

We have fixed the dependency array in the Dashboard and are auditing the remaining API call sites for the same pattern. Client retries against the control plane will use randomized exponential backoff, so a Tenant Service restart no longer arrives as a synchronized re-authentication of every open dashboard.
