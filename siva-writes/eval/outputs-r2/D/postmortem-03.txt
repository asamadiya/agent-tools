Cloudflare 500 errors, 5 December 2025

Between 08:47 and 09:12 UTC on 5 December 2025, about 28% of the HTTP traffic Cloudflare serves returned HTTP 500, because an internal configuration change that touched no customer traffic reached the entire fleet in seconds and hit a latent nil dereference in our Lua proxy. This was not an attack, and no customer data was exposed or lost. We apologise to every customer whose users saw those errors.

The work that led here started as a security fix. Our WAF buffers HTTP request bodies in memory so rules can inspect them, and that buffer had been 128KB. Covering customers against CVE-2025-55182, a critical React Server Components vulnerability, requires inspecting bodies up to the Next.js default limit of 1MB, and we began raising the buffer to that size. That first change went out through our gradual deployment system, which stages a change across a small fraction of the fleet before widening it.

An internal WAF testing tool turned out not to support the 1MB buffer, and the change that disabled that tool is the one that broke your traffic. The tool sits outside the request path and has no effect on customer traffic, which is why disabling it read as a low-risk action. We made the disable through our global configuration system, which performs no staged rollout and reaches every machine within seconds. A change with no customer-facing blast radius was pushed by the mechanism with the largest one.

The disable was implemented as a killswitch in our rulesets system, and killswitches had never been applied to a rule of this kind. A rule's action is block, log, skip, or execute, where execute triggers evaluation of a sub-ruleset. The killswitch rewrites the action to skip, and the skip was honoured correctly. Result-processing code downstream still read `rule_result.execute` on that rule, a field that no longer existed once the action was no longer execute, and indexing nil in Lua raises an error. The failure surfaced at `init.lua` line 314 in our FL1 proxy and each affected request terminated as an HTTP 500.

That line of code had been wrong for years and nothing had ever reached it, because no killswitch had previously been applied to a rule with action execute. Coverage of the rulesets system was real, and it was coverage of the combinations operators had actually produced. FL2, the Rust reimplementation of the proxy, constructs the result differently and does not carry the bug.

Customers on FL1 with the Cloudflare Managed Ruleset deployed saw every request fail, not a fraction of them. A handful of endpoints served ahead of the ruleset, such as `/cdn-cgi/trace`, continued to return 200, which is why some health checks stayed green through the outage. Traffic on our China network was unaffected. Customers on FL2 and customers without the Managed Ruleset saw no impact.

Automated alerts declared the incident at 08:50, three minutes after impact began. We reverted the configuration change at 09:11 and propagation completed at 09:12, a total of 25 minutes of elevated 500s. Detection was fast and diagnosis was the long pole: the failing proxy line pointed at result processing, and the cause was a configuration push made 21 minutes earlier in a different system.

Three changes follow from this. Killswitches will be routed through the gradual deployment system, because a change whose payload is safe can still be unsafe in how it arrives. Result-processing code in FL1 will check field presence before dereference on every action type, and we are auditing the other action transitions for the same shape of bug. We are accelerating the migration of remaining FL1 traffic to FL2, which both removes this class of defect and shrinks the surface on which we maintain two proxies.
