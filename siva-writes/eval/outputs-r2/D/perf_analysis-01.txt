Cassandra on Ubuntu: 32% of the CPU was asking what time it is

A Cassandra cluster moved from CentOS to Ubuntu in 2014, write latency rose by over 30%, and a CPU flame graph put 32.1% of the on-CPU samples inside os::javaTimeMillis() calling gettimeofday(2). Basic stats had already shown CPU consumption up by over 30% on the same instances, which is the same size of regression as the latency, and that agreement is what pointed at a CPU profile as the next step; a lock or GC problem would have moved latency without moving CPU by the same fraction.

The obvious explanations were dead within a few minutes. top(1) on an Ubuntu instance showed one process consuming CPU, the Cassandra JVM, which rules out an Ubuntu daemon that had quietly moved in and started charging us for itself. execsnoop(8), the Ftrace version at the time, showed no short-lived processes, which closes the gap top(1) leaves: a process that lives for 40 milliseconds and exits never appears in a one-second refresh but can still burn a core. The extra 30% was inside the application we had not changed, on a kernel and userland we had.

We collected flame graphs on one CentOS instance and one Ubuntu instance in parallel, because these are production nodes taking production traffic and the traffic mix moves with the time of day. Profiling one host and then the other an hour later measures the hour as much as the distro. Running both at once costs nothing and removes the whole class of objection.

Broken Java stacks are what made the difference visible. This was before -XX:+PreserveFramePointer, and the JVM frames collapsed into one or two green blocks in both profiles instead of a tower of Java method names. That breakage is normally the thing that ends an investigation, and here it helped: with the Java frames above it erased, every os::javaTimeMillis() call site merged into a single leaf block instead of scattering across dozens of thin stacks too narrow to notice. One block in the middle of the Ubuntu flame graph was 30.14% wide. Searching the profile for the function summed the remaining slivers to 32.1%.

The path under that block explains why a timestamp costs anything at all. os::javaTimeMillis() calls gettimeofday(2), and on the Ubuntu instance the frames above gettimeofday were tracesys() and syscall_trace_enter/exit -- the kernel's syscall tracing entry and exit hooks, which run per syscall and are not free. Cassandra takes a timestamp on essentially every write, so a per-call regression of a microsecond scale multiplies by the write rate and lands directly on write latency. Nothing about the workload changed; the per-call cost of one of its hottest primitives did.

Two theories fit that path, and the profile favors one without settling it. Theory A: something on Ubuntu enabled syscall tracing, auditing or apparmor being the candidates, which puts tracesys() in every syscall's path. Theory B: fetching the time is slower on Ubuntu for a different reason, a library change or a kernel and clocksource change that pushes the call into the kernel in the first place. The frame widths favor A, since the traced entry and exit frames carry visible width of their own and do not sit as thin decoration above a fat gettimeofday. The Ubuntu profile also shows a vDSO frame with the syscall still above it, meaning the vDSO fast path was entered and did not serve the request: Xen pvclock had no vDSO support at the time, and a Xen guest therefore traps into the kernel for the time regardless of distro. That detail explains why the call is a syscall on both, and therefore why it was expensive enough on CentOS to be worth making more expensive on Ubuntu.

The 32.1% is a share of what perf(1) could see, which is less than everything. These are EC2 Xen guests, and the profile used software cpu-clock soft interrupts, not hardware NMI sampling. Kernel paths that run with interrupts disabled are invisible to that sampler, and so is all time spent in the hypervisor. The number is a lower bound on the time-of-day path, not a measurement of the machine, and if the regression had been in an interrupts-disabled path the profile would have shown a clean CentOS-shaped graph on both hosts.

Check the clocksource and the syscall-tracing configuration before anything else when a distro migration moves CPU on an unchanged workload. This one cost a day and returned nothing to the people who normally have the answer: colleagues had not hit it, and the internet had nothing connecting os::javaTimeMillis, clocksource, tracesys, Ubuntu, EC2 and Xen. Two changes generalize past this bug. Profile the old and new hosts in parallel on live traffic rather than in sequence. State what your sampler cannot see next to the percentage it reports, because on a Xen guest with cpu-clock sampling a percentage is a percentage of the visible half.
