Invest in the machinery that tells a coding agent it is wrong: the availability of accurate feedback, not the human difficulty of a task, sets the limit on what coding agents can do.

Agents already sort themselves along this line. They stay unstuck when error messages are good, because a good message names the defect and the line it lives on. They produce better Rust than they do most languages, because the compiler signals whole classes of incorrectness explicitly and immediately. They do well on performance work wherever a benchmark exists, and property-based testing has turned out to be unusually valuable to them. They do badly on architecture, where feedback is of the know-it-when-I-see-it kind, and badly on concurrent programs, where it arrives as silent data corruption at runtime, if it arrives at all.

The mechanism is that an agent improves only by proposing something and being corrected, so the rate and the fidelity of correction bound how far it gets. An oracle that answers on every iteration, and that localizes the fault instead of returning a single bit, turns an open-ended search into a hill climb. The borrow checker is such an oracle. A design review is not: it arrives days later, it judges the whole artifact at once, and two reviewers disagree.

This inverts the ranking we are used to. Take two problems: build a delightful, ergonomic photo-editing website, and build a correct, high-performance storage engine at the scale of RocksDB or InnoDB. Today's open-loop models get much closer to the website in a single shot. Over the long run the storage engine becomes the easier of the two.

The reason is that the website's loop terminates in a person and the storage engine's does not. Humans are slow, squishy, inconsistent feedback providers, and a person cannot tell you which of forty changes made the interface feel worse. The storage engine has a specification with three machine-checkable parts -- the API, the safety properties, and the liveness properties -- so a simulator with fault injection can run that specification thousands of times overnight with nobody watching.

We should therefore fund oracles, not more agent orchestration. At compile time that means Rust, Hydro, and Verus, each of which moves a property from something a reviewer checks into something the toolchain refuses to build without. At modelling time it means TLA+ and P, which give concurrency the explicit failure signal it currently lacks. Ahead of implementation it means spec analyzers of the kind Kiro ships, which catch an underspecified requirement before an agent spends a week satisfying the wrong one. At runtime it means deterministic simulators, fault injectors, and high-fidelity mocks.

Rank any candidate investment by three questions. Can a machine decide the answer is wrong? How long does that take, counted in seconds of agent wall clock? Does it say which part is wrong, or only that something is? A tool that answers yes, seconds, and localized is worth more than a tool that makes the agent marginally cleverer, because the second kind of improvement is capped by the first.

Treat this as a hypothesis with an outstanding test. The evidence above is observational, drawn from where agents currently succeed and fail, and it is consistent with a weaker story in which agents are simply better at code with more of it on the internet. Pick two of our in-flight workstreams -- one with a machine-checkable specification, one whose acceptance criterion is a human reaction -- and measure agent-completed tasks per week in each for a quarter.
