Diagnosis: the 100-Gbyte uploads are slow because the file does not fit the page cache

The 100-Gbyte uploads take hours because the file is larger than the 48 Gbytes of page cache on the instance and the service makes multiple passes over it, so every pass after the first re-reads the file from disk, while the 40-Gbyte files fit and are served from memory on every pass. That is the whole finding; the rest of this is how we got there and what we think you should do about it.

The first clue was `free -m`, which showed a 64-Gbyte machine with almost nothing free and almost everything in the cache: total 64,414 MB, used 15,421 MB, free 349 MB, buff/cache 48,643 MB, available 48,409 MB, swap 0. A machine in that state is not short of memory in any way that would show up as swapping or as an OOM kill, and the service was not being killed, which is why nobody had looked at memory before. What the numbers say is that the page cache had grown to fill essentially all the memory the workload was not using, roughly 48 Gbytes, and that 48 is a number sitting between the file size that is fast (40) and the file size that is slow (100). That is suggestive and nothing more, which is why we then measured the cache directly.

`cachestat` confirmed cache busting on a live 100-Gbyte upload. Per-second hit ratios over the sample were 74.1%, 9.7%, 6.5%, 12.0%, 34.5%, 7.0% and 11.1%, with misses running from 632 up to 23,341 per second, BUFFERS_MB at 17 and CACHE_MB at about 48,000. On a workload you want to be reading from memory, hit ratios in the upper 90s are the expected reading, and a single-digit hit ratio means that nearly every page the code asks for has already been evicted and has to come back off the disk. The mechanism is ordinary LRU behaviour against a working set larger than the cache: a sequential pass over 100 Gbytes through a 48-Gbyte cache evicts the head of the file to make room for the tail, so by the time the next pass starts at the head, the head is gone, and the hit ratio collapses to roughly the fraction of the file the cache can still hold.

The control test on a 32-Gbyte upload is the cleaner half of the evidence: `cachestat` reported a 100.0% hit ratio with 0 misses in every second sampled, hits between 33,424 and 65,158 per second, BUFFERS_MB 41 and CACHE_MB about 33,680. `free -m` on that run showed used 18,421 MB, free 11,218 MB and buff/cache 34,773 MB, leaving the file resident with 11 Gbytes of headroom, and `iostat` showed almost no disk I/O at all. Zero misses across the whole run means the passes are free after the first read: the code can walk the file as many times as it likes and never touch the disk again.

The fastest fix is a larger-memory instance, one whose page cache comfortably exceeds 100 Gbytes, which restores the 32-Gbyte behaviour without anyone changing code. The durable fix is in the service: process the file in parts sized to fit the cache instead of making multiple passes over the whole thing, which bounds the working set and does not bet that the instance is always bigger than the largest input. The instance change buys time and moves the cliff; it does not remove it, and the next customer with a 400-Gbyte file will find it again.

One caveat on the tooling. `cachestat` was the tool that settled this, and it is still experimental, built under tight constraints on overhead and on the Ftrace function profiler. At the LSFMMBPF 2019 keynote we argued to the Linux mm engineers in the room that page cache hit statistics are needed often enough to belong in `/proc`. They pointed out real difficulties in exposing them properly, and page cache counters sit on a hot path, where adding a counter is not free.
