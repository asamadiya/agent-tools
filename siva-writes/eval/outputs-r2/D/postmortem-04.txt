BYOIP prefix withdrawal, 20 February 2026 (all times UTC)

A cleanup sub-task in our Addressing API withdrew roughly 1,100 customer BYOIP prefixes, about 25% of all BYOIP prefixes, because a missing query-string value was read as a filter matching every prefix rather than none. Withdrawals ran from 17:56 to 18:46. The last prefixes were restored at 23:03, 5 hours and 15 minutes after the outage began at 17:48.

Customers running Bring Your Own IP lost reachability on the affected prefixes, and the failure mode was a hang and not a refusal. When a prefix is withdrawn from BGP, routers do not conclude that the destination is gone; they try the next-best path they hold, then the next, which is path hunting. Client connections kept searching for a route and stalled until their own timeouts fired. The first reports we received described slow sites, not dead ones.

Visitors to the one.one.one.one website received HTTP 403 with an Edge IP Restricted message, while DNS resolution kept working throughout. The 403 is the edge declining to serve a hostname on an IP whose binding had been deleted alongside the prefix. Resolver traffic on 1.1.1.1, including DNS over HTTPS, was unaffected for the full 5 hours 15 minutes. If you watched us through DNS queries you saw nothing; if you watched us through the website you saw a hard failure.

The defect is one line of query-parsing semantics. The new sub-task issued GET /v1/prefixes?pending_delete with no value after the equals sign. On the server, Query().Get("pending_delete") returns an empty string both when the parameter is absent and when it is present and empty, and the handler treats an empty string as an unset filter. The API therefore returned every BYOIP prefix it had. Of the 6,500 prefixes we advertise to a given peer, 4,306 are BYOIP, and the sub-task read that entire list as a deletion queue and started working through it.

The blast radius follows from what the Addressing API is: the authoritative source for customer IP addresses, pushing changes to the edge on write. No reconciliation step sits between the API's view and the edge's view where a second observer could inspect a diff of that size. Each row the sub-task deleted removed a prefix and its dependent service bindings, and each removal became a BGP withdrawal within seconds. In 50 minutes the loop got through about 1,100 of the 4,306.

Detection was quick and the stop was not. The code merged on 5 February at 21:53 and deployed at 17:46 on 20 February, and impact began 10 minutes later at 17:56. We engaged on the one.one.one.one failures at 18:13, opened an internal incident at 18:18, and paged the Addressing API team at 18:21. An engineer terminated the sub-process at 18:46, 50 minutes after the first withdrawal, and mitigation was in place at 19:11. Restoration was the long tail: about 800 prefixes were back by 20:20, and the remaining 300 needed manual work that finished at 23:03.

Our tests covered the customer self-service journey and never covered a task runner mutating customer data with no explicit input. Staging data and mocks were thin enough that a query returning 4,306 rows where zero was expected looked like a healthy query. A self-service test asserts that deleting a prefix the customer named deletes that prefix, and that assertion held here. Nothing asserted the property we needed: a deletion request that names nothing deletes nothing.

We are changing three things. The Addressing API now rejects a filter parameter that is present with an empty value instead of treating it as absent, which turns this class of bug into a 400 at the first request. Automated deletion paths carry a cap on how many objects a single run may remove, and a run that reaches the cap halts for human review. Our test suite gains cases for task runners that mutate customer data, beginning with the empty-selector case that produced this outage.

BYOIP customers need take no action now, and your prefixes are advertised as they were before 17:48. We published self-remediation guidance at 19:19 for customers who wanted to re-announce ahead of our own restoration, and that guidance is no longer required. If you are still seeing a withdrawn prefix, or a service binding that did not come back with it, tell us and we will restore it by hand as we did for the final 300.
