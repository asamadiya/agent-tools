search-federator canary 2026.9.3: schema-cache thrashing, interceptor reverted Sep 15

The 2026.9.3 canary raises p99 response time to 311 ms against 184 ms on the control fleet, a 127 ms increase caused by a 512-entry schema cache holding a 3,400-schema working set, and we reverted the new gRPC interceptor from the release branch on Sep 15. The build has run on 4 of 240 production hosts since Sep 8, carrying 1.7% of traffic. The service SLO is p99 under 250 ms; the canary hosts miss it by 61 ms. Error budget consumed to date: zero, because 4 hosts at 1.7% of traffic do not move the fleet-wide percentile. Owner is Dan Ortiz.

The regression is entirely in the tail. p50 moved from 41 ms to 42 ms. The interceptor's own median cost is 0.9 ms and its p99 cost is 94 ms, which accounts for most of the 127 ms p99 delta and for essentially none of the p50 delta. The 94 ms is schema recompilation, which happens on a cache miss and runs synchronously on the serving path before the response goes out.

The miss rate follows directly from the cache size. The interceptor validates every response payload against a JSON schema, the cache is a 512-entry LRU, and the canary's working set is roughly 3,400 distinct schemas. That leaves 15% of the working set resident at any moment. Measured hit rate on canary is 71%. At 2,900 QPS per host that is about 840 recompilations per second per host, each of them a full schema compile in front of a client waiting for a response. An LRU under a uniform-ish access pattern over 3,400 keys with 512 slots evicts entries before they are reused, and the hit rate lands near the residency ratio well short of 100%.

The pre-release load test missed this because it exercised 300 schemas. Three hundred fit inside 512 entries, every schema stayed resident after first use, and the test reported a 99.6% hit rate, 28.6 points above what production delivered. The test measured the interceptor with a warm cache and no eviction. It never measured the operation that dominates the tail. Any load test for a cached component has to take schema cardinality from production traffic, and ours took it from a fixture list.

Four changes go into the re-canary on Sep 22. The interceptor is out of the release branch as of Sep 15. The cache goes to 8,192 entries, which covers the observed 3,400-schema working set with 2.4x headroom for growth. Validation moves behind a sampling flag set to 1%, so a future miss storm costs one request in a hundred instead of 29 in a hundred. The load test gets its schema set sized from production cardinality.

Two numbers gate the Sep 22 re-canary. Cache hit rate must hold above 99% at 2,900 QPS per host against the full production schema set, and canary p99 must land under 250 ms. If hit rate comes in below 99%, the working set is larger than 3,400 and the 8,192-entry cache is the wrong size, not a bigger version of the right one.

SLO owners need no action this week. The canary consumed zero error budget, the reverted interceptor ships in no build, and the Sep 22 re-canary runs on the same 4 hosts at 1.7% of traffic. We will report hit rate and p99 from those hosts at the following review.
