Frame pointer overhead

Frame pointers compiled into everything -- libc and Java both -- cost under 1% across the Netflix production rollout, often too little to measure at all, and the one workload that came in at 10% is a case where we could not attribute the 10% to anything.

That workload was unusual in a way that is easy to state. Its stack traces ran more than 1000 frames deep, generated through Groovy, deep enough that Linux's perf profiler could not walk them, and Arnaldo Carvalho de Melo at Red Hat added a new sysctl, kernel.perf_event_max_stack, specifically so that one Netflix workload could be profiled at all. The instance was also a virtual machine with no low-level hardware profiling available, which means there was no way to run cycle analysis on it, and therefore no way to establish that the whole 10% came from frame pointers rather than from anything else that differed on that host. The number is real. The attribution is not.

How much frame pointers cost depends on the workload, and the independent numbers that have come back from outside Netflix are roughly 1% and roughly 2%. Those are the same order as the under-1% production result, measured by people with different compilers, different services and no stake in the Netflix rollout, which is the main reason to believe the production number generalizes.

Microbenchmarks sit at the bad end of that range and can show 10%, and cache geometry explains why. A microbenchmark usually reduces to one small function executed in a loop, so every instruction added to that function is added to the whole measured program. The push and pop of %rbp per frame are a few bytes each. Add a few bytes to a hot function and you risk pushing it past the point where it stays warm in L1, or across a cache line boundary it previously fit inside, and throughput falls by an amount that has nothing to do with the arithmetic cost of two instructions.

Python's scimark_sparse_mat_mult is that mechanism made concrete, and it also touched 10%. Andrii Nakryiko at Meta ran it down to a single large function in which gcc, denied %rbp as a general register, stopped addressing locals as %rsp-relative and started computing offsets from %rbp. The %rbp form needs more bytes to encode the same accesses. The cost was not the prologue and epilogue at all; it was every local variable access in the body of one large function getting longer. That has since been fixed, which is what let Python turn frame pointers back on by default.

Treat a 10% microbenchmark result as the start of an investigation. Count the instructions in the hot function with and without frame pointers. Read the PMCs: cycles, instructions retired, L1i misses, and the front-end stall counters. Run PEBS and find the instruction the stalls land on. Either the added bytes show up as a front-end or cache effect on one specific function, in which case you have the Python result again and a compiler bug to file, or they do not, in which case the headline number is measuring something else on the machine. The headline number alone does not distinguish these.

Set the cost against what frame pointers buy, which is profiles that find wins in the range of 5% to 500%. A 1% tax that unlocks a 5% win pays for itself five times over, and the wins at the top of that range are not reachable at all without knowing which stack the cycles are in. Even the 2% figure from the pessimistic independent reports clears the bar by a wide margin, and the 10% outliers both turned out to be specific, diagnosable, and in the Python case already repaired.

Compile with frame pointers by default. Zero overhead would be better, and later technologies -- SFrame, better ORC coverage, whatever comes after -- may get there. Today nothing available finds a 5% to 500% win as reliably as a working stack walker, and paying under 1% for one is the cheapest instrumentation in the system.
