The Xen clocksource, not the JVM: why gettimeofday cost 0.68 us on Ubuntu

The third of Cassandra's CPU that was disappearing into os::javaTimeMillis() was not a JVM cost at all, it was the Xen paravirtual clocksource, and echoing tsc into current_clocksource took the call from 0.68 us to 33 ns and dropped production write latency 43%.

We had a flame graph pointing at os::javaTimeMillis() and no microbenchmark for it, since nobody publishes one for a call that is supposed to be free. TimeBench.java calls System.currentTimeMillis() 100,000,000 times in a loop, compares each result against 87362, and does a println inside the comparison branch, because a loop whose result is never observed is a loop the JIT is entitled to delete. The comparison and the branch cost something, which makes the measured per-call number slightly pessimistic, and that is the right direction to be wrong in when you are trying to establish that a call is expensive. Run it under time(1) and read all three lines, not just real.

On the same instance type, CentOS took real 12.989s, user 3.368s, sys 18.561s, and Ubuntu took real 1m8.300s, user 38.337s, sys 29.875s. That is 0.13 us per call on CentOS against 0.68 us on Ubuntu, a factor of 5.2, for a call that on bare metal has no business touching the kernel at all. The sys column is the interesting one: 18.561s of system time on the fast distribution already says that every currentTimeMillis() is entering the kernel, and 100,000,000 kernel entries is a sufficient explanation for a third of a database's CPU.

The JVM was not implicated, because a C program calling gettimeofday(2) in the same loop reproduced the same per-call costs. Compile it -O0 so the loop survives, and disassemble the binary afterwards to confirm the compiler emitted the loop you wrote. A benchmark this short is small enough to read in full at the instruction level, which is the only way to be sure you are timing the call and not an empty loop that the optimizer folded into a constant.

The clocksource, not the distribution, was the variable. /sys/devices/system/clocksource/clocksource0/available_clocksource listed xen, tsc, hpet, acpi_pm, and current_clocksource read xen, which matches the pvclock_clocksource_read() frame sitting in the flame graph directly under os::javaTimeMillis(). Echo tsc into current_clocksource and the change takes effect immediately, with no reboot and no instance replacement.

TimeBench then ran real 0m3.370s, user 3.353s, sys 0m0.026s. That is 33 ns per call, 20.3x faster than the same binary on the same instance ninety seconds earlier, and 3.9x faster than CentOS on xen. Read the sys column again: 29.875s collapsed to 0.026s, a factor of 1,150, and nearly all of the win is there. Under tsc the kernel is not involved. A time read is a single RDTSC instruction, dispatched through vDSO, with no syscall, no hypervisor page, and no trap out of the guest. Under xen it is a read of a shared pvclock structure that the hypervisor maintains, and pvclock_clocksource_read() is where the 0.65 us of difference lives.

The 33 ns figure is itself inflated by the benchmark. At that per-call cost the comparison, the branch, and the loop bookkeeping are a meaningful fraction of what time(1) is measuring, and partially unrolling the loop would tighten the number. We did not bother, because the decision did not turn on whether the true cost is 33 ns or 25 ns.

The reason to hesitate on tsc is clock drift, and the evidence against it turned out to be thinner than its reputation. A processor engineer at a conference said tsc had been stable for years on current parts and knew of no public reference that says so, which is an uncomfortable basis for a fleet-wide change. What made it a reasonable bet is that Netflix's cloud is built to tolerate a node returning wrong answers, so a drifting instance is a failure mode the system already handles, and the experiment is one echo to revert.

Production agreed with the microbenchmark. Cassandra write latencies dropped 43%, slightly better than the CentOS nodes were doing, and os::javaTimeMillis() fell from roughly a third of CPU to 1.6%, with only a vdso frame above it in the flame graph. That last detail is the confirmation that matters more than the latency number: the profile now shows the mechanism we predicted, a userspace time read with no kernel frame under it.

Check current_clocksource on every Xen guest you run. It is one file read, the fix is one file write, and on a workload that timestamps every request the difference is a factor of 20 on a call that shows up millions of times a second.
