ZFS burned 38% of a Netflix microservice fleet's CPU time evicting from a cache that held nothing, on instances where no ZFS filesystem was mounted at all. The team that owned the metrics-ingestion service had updated their BaseAMI, watched system CPU climb, and reported that ZFS was eating over 30% of their capacity. That number was the first thing worth disbelieving: ZFS has to be badly misconfigured before the ARC can cost that much CPU, and nothing in a metrics ingestion path should touch a filesystem cache that hard. The number was also real, which is the useful part of the story.

Atlas put 38% of CPU time in sys, which is high enough for a Netflix cloud workload to be diagnostic on its own. Most services here spend their kernel time in the network stack and in the allocator, and a sys fraction that large means something in the kernel is spinning on work the application never asked for. The next step was not an SSH session with mpstat(1) and perf(1). Netflix's flame graph fetch path (Vector at the time, FlameCommander later) renders a whole-instance CPU profile from a browser, and for a question of the form "which kernel path is this", a flame graph answers in one screen what a profiling session answers in twenty minutes.

The flame graph showed two orange kernel towers, left and right. The left tower was `arc_reclaim_thread`. The right tower entered `spl_kmem_cache_reap_now()`, a second ZFS memory-freeing path, and the two were almost certainly contending on the same locks, which is why the cost showed up twice. Both towers are ARC machinery. The Adaptive Replacement Cache is ZFS's main in-memory cache, and `arc_reclaim_thread` runs `arc_adjust()` to evict buffers and hold the system above a free-memory threshold, either periodically or when woken by memory pressure.

There is a known way to make `arc_reclaim_thread` burn CPU, and it did not apply. Set the record size small enough, say 512 bytes, and a modest working set becomes millions of buffers, each of which eviction has to walk. The ZFS default record size is 128 Kbytes and the practical floor for tuning is 8 Kbytes, so a buffer-count explosion would have required somebody to have deliberately configured one. Nobody had.

The first real theory was containers, and the team killed it in two sentences. A new infrastructure project at Netflix was using ZFS to back container filesystems, and heavy container churn means heavy filesystem creation and destruction, which would plausibly keep ARC reclaim busy. The team said they were not running containers. Then they said they were not using ZFS at all. `df -h`, `mount`, and `zfs list` on two instances agreed: no ZFS filesystems mounted. `/proc/spl/kstat/zfs/arcstats` agreed harder, with every counter at zero, hits 0 and misses 0 and the rest of them 0. The cache that was consuming 38% of the CPU had never serviced a single request.

The mechanism is in the eviction path's list selection, and it was introduced by a performance feature. To cut lock contention on a busy ARC, a multilist change split the ARC's lists one per CPU, and eviction picks which list to evict from at random. The random source is the cryptographically secure one: the flame graph's towers resolved through `get_random_bytes()` into `extract_entropy()`. So on these instances ARC detected low system memory, paid the full cost of a cryptographic draw to choose a per-CPU list, found that list empty, and did no work. Then it did it again. The per-pick cost scales with the number of lists and the entropy call, and the work accomplished scales with the number of buffers, which was zero. An empty cache is not a free cache.

Read `arcstats` before you accept that a cache is the problem. Four counters at zero would have separated "ARC is working too hard" from "ARC is spinning on nothing" in the first minute, and the flame graph would then have been confirmation instead of the whole investigation. The behaviour was filed as ZFS issue #6531, and the first fix made `arc_reclaim_thread` bail out early when ZFS is unused, which is the narrow repair. The broader one is that a contention fix that adds a per-operation cost has to be checked against the case where the operation accomplishes nothing.
