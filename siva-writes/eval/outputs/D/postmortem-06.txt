Cloudflare Dashboard and API outage, 12 September 2025

On 12 September 2025, the Cloudflare Dashboard and much of our public API returned 5xx errors from 17:57 to 19:12 UTC, because a bug in the Dashboard's own code flooded the Tenant Service that authorizes every API request. The bug was ours, in a Dashboard version we shipped at 16:32 UTC. We are sorry for the disruption to customers who needed to change configuration during those 75 minutes.

No network traffic was affected. Our control plane and data plane are strictly separated, so the services that proxy, cache and protect customer traffic kept running on their own path and never consulted Tenant Service. If you did not attempt a configuration change or an API call during the window, you saw nothing.

The Dashboard bug was a React `useEffect` whose dependency array contained an object recreated on every state or prop change. React compares dependencies by reference, so it treated that object as new on every render and re-ran the effect, which called `/organizations`. One user session therefore issued many calls per render instead of one per page load, and each failed call was retried. The Dashboard was generating its own load, and the load grew as the calls started failing.

Tenant Service sits in the API request authorization path, and requests it cannot evaluate return 5xx. It is a Go process running on Kubernetes in a subset of our datacenters. At 17:50 UTC we deployed a new Tenant API Service version into a service already carrying the amplified Dashboard traffic; by 17:57 UTC Tenant Service was overwhelmed and Dashboard availability began dropping. Because the same service authorizes API calls made outside the Dashboard, customers using the API directly saw 5xx errors from a defect they had no part in.

Our first mitigations restored the API and left the Dashboard broken. We added pods and applied a global rate limit, and by 18:17 UTC the API had returned to 98% availability while the Dashboard had not recovered. Restarting Tenant Service produced a thundering herd: every open Dashboard re-authenticated at once, and the render loop multiplied that burst instead of letting it drain. At 18:58 UTC we shipped a change to remove the erroring codepaths and it increased API impact. At 19:01 UTC we published a temporary rate-limiting rule. At 19:12 UTC we reverted the changes and Dashboard availability returned to 100%.

Two gaps turned a bad deploy into a 75-minute outage. First, Argo Rollouts, which automatically rolls back a deployment when it detects errors, had not yet been adopted for Tenant Service; it would have reverted the 17:50 UTC update without a human in the loop. Second, our telemetry could not distinguish a retry from a new request, so responders looking at request volume could not tell whether they were watching real demand or a feedback loop feeding on its own failures. That ambiguity is why we spent the hour after 17:57 UTC adding capacity to a service whose load was self-generated.

We are making the following changes. We are onboarding Tenant Service to Argo Rollouts so a deploy that raises the error rate rolls back automatically. We are instrumenting retries distinctly from first attempts across the API authorization path, so responders can read a feedback loop off a graph. We are adding API call-rate tests to the Dashboard build so a render-loop regression fails before it ships. We are giving Tenant Service the capacity headroom and admission controls to survive a client that misbehaves this way, since the next one will not look like a `useEffect` dependency array.
