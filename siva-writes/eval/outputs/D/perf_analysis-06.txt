Page cache busting explains the 100-Gbyte upload times

The 100-Gbyte uploads take hours because the file is larger than the 48 Gbytes of page cache the instance has available, so the service's repeated passes over the file come off disk, while a 40-Gbyte file fits in cache and every pass after the first is served from memory.

The first thing that pointed here was `free -m` on the problem instance: total 64,414 MB, used 15,421, free 349, buff/cache 48,643, available 48,409, swap 0. A 64-Gbyte machine with 48 Gbytes already in the page cache and 349 MB free is a machine whose cache is full and being churned. Put the two file sizes next to that 48 Gbytes and the theory is obvious -- 40 fits, 100 does not -- but the memory numbers alone cannot distinguish a full cache that is working from a full cache that is thrashing, since a healthy cache is also full.

`cachestat` settled it. On a 100-Gbyte upload it reported per-second hit ratios of 74.1%, 9.7%, 6.5%, 12.0%, 34.5%, 7.0% and 11.1%, with misses climbing from 632 to 23,341 per second, BUFFERS_MB 17 and CACHE_MB around 48,000. A healthy file workload sits in the upper 90s. Ratios in the single digits mean nearly every page the service asks for has already been evicted, and each of those misses is a disk read the service then waits on.

The control test is what makes the mechanism, and not just the correlation, defensible. On a 32-Gbyte upload, `cachestat` reported a 100.0% hit ratio with 0 misses in every second sampled, hits running 33,424 to 65,158 per second, BUFFERS_MB 41 and CACHE_MB about 33,680. `free -m` on that run showed used 18,421, free 11,218, buff/cache 34,773, and `iostat` showed almost no disk I/O at all. The 32-Gbyte file was read from disk once and then processed entirely out of memory, however many passes the code made over it.

The mechanism is working set against cache size, not file size against anything. The service makes several passes over the whole file. When the file is smaller than the cache, pass 2 through pass N find every page resident and cost memory bandwidth. When the file is larger than the cache, each pass evicts exactly the pages the next pass is about to want, because the head of the file is gone by the time the tail is read, so every pass after the first costs a full re-read from S3-backed storage. The cliff sits where the file crosses roughly 48 Gbytes, and 40 versus 100 Gbytes straddles it.

The quickest fix is an instance type whose memory holds a 100-Gbyte file, which needs more than 100 Gbytes of usable page cache once the 15 Gbytes of process memory is accounted for. That is a config change, it is testable in an afternoon, and `cachestat` tells you immediately whether it worked: the hit ratio should go to the upper 90s and `iostat` should go quiet.

The durable fix is in the code, which should be written against the memory constraint instead of against the file. Process the file in parts, finishing all the work on one part before moving to the next, and the working set becomes the part size, which you control. That version runs on the current instance type and keeps running when someone uploads 200 Gbytes.

One caveat on the tool. `cachestat` was the tool that closed this, and it is still experimental, built under the constraints of low overhead and the Ftrace function profiler. The argument for putting these statistics in `/proc` was made at the LSFMMBPF 2019 keynote in Puerto Rico with Linux mm kernel engineers in the room; they pointed out real difficulties, and page cache counters sit on a hot path, so the instrumentation is not free.
