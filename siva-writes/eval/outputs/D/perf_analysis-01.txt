Reading the clock, not writing to the database: where Cassandra's 30% Ubuntu regression went

A Cassandra cluster that moved from CentOS to Ubuntu spent 32.1% of its CPU inside os::javaTimeMillis(), which is where the extra 30% of write latency and the extra 30% of CPU consumption went, and which is a cost the database pays once per timestamp it stamps. Nothing in the Cassandra code changed across the migration. What changed was how much a single call to fetch the current time costs on the new image.

The first two things we checked ruled out the explanations that cost nothing to check. top(1) on the Ubuntu instances showed only the Cassandra JVM consuming CPU, so no Ubuntu service that CentOS did not ship was quietly taking a third of the machine. execsnoop(8), in the Ftrace version we had then, showed no short-lived processes, which rules out the class of regression where a per-request fork or a monitoring agent that lives for 40ms never appears in a one-second sample of top. Both of those tools answer "is it someone else" and neither of them can say anything about where inside the JVM the time goes.

CPU flame graphs collected on one CentOS instance and one Ubuntu instance in parallel put the difference in a single frame. Collecting in parallel matters more than it sounds like it should: these are production instances taking live traffic, the traffic mix moves with time of day, and a CentOS profile from 09:00 compared against an Ubuntu profile from 14:00 is a comparison of two workloads as much as two operating systems. With the profiles taken over the same wall-clock window, the Ubuntu graph carried a 30.14% block in the middle that the CentOS graph did not, and searching the graph for the same symbol brought the total to 32.1%.

We could read that block only because Java stacks were broken, which is the part of this investigation that was luck. This was before -XX:+PreserveFramePointer, so the profiler walked one or two green frames and then lost the tower of Java methods above them. Working stacks would have scattered os::javaTimeMillis() across every Java call site that asks for the time, each one a thin sliver a fraction of a percent wide, and no sliver would have been wide enough to draw the eye. The breakage merged all of those call sites into one 30.14% block with a readable label. A flame graph is a width-sorted argument, and losing the frames above a function is what made this function wide.

The mechanism is that os::javaTimeMillis() calls gettimeofday(2), and on this image gettimeofday leaves userspace. Above the vDSO frame in the Ubuntu graph sat the syscall itself, then tracesys(), then syscall_trace_enter() and syscall_trace_exit(). The vDSO exists so that a clock read is a few nanoseconds of userspace arithmetic against a page the kernel maps read-only into every process, and Xen pvclock did not support the vDSO path at the time, so each read becomes a real syscall on a Xen guest. Cassandra timestamps every write it accepts, which turns a per-call cost of a few hundred nanoseconds into a fixed tax on write throughput.

Two explanations fit that stack and we did not fully separate them. Either Ubuntu has syscall tracing enabled where CentOS does not, from auditd or apparmor, and the tracesys entry and exit hooks are the added cost; or fetching the time is slower on Ubuntu for a library or clocksource reason and the syscall is incidental. The relative frame widths favored tracing, since tracesys and its enter/exit children accounted for the bulk of the block and the clocksource read underneath them was narrow. That is evidence from one profile pair and it is weaker than a controlled A/B with auditing disabled, which is what we would want before writing this into an image policy.

The profile has a known blind spot and it points the same direction the conclusion does, which is the uncomfortable part. These are EC2 Xen guests, so perf(1) sampled with software cpu-clock soft interrupts and not hardware NMIs. Software sampling cannot fire while interrupts are disabled, so kernel paths that run with interrupts off are systematically under-counted, and all hypervisor time is invisible entirely. The 32.1% is therefore a floor on syscall-related cost and not an estimate of it.

Search returned nothing on any combination of os::javaTimeMillis, clocksource, tracesys, Ubuntu, EC2 and Xen, and colleagues running the same migration had not hit it. Treat that as a statement about how the fleet is profiled and not about how rare the bug is. Every service on a Xen guest that reads the clock at request rate pays this, and a 30% CPU regression with no rogue process and no short-lived process is close to invisible without a differential flame graph.

So the check to run before attributing a cross-distribution regression to the application: take parallel CPU flame graphs on one instance of each image, then compare the clocksource and the vDSO capability between them.
