Remediation: BYOIP prefix withdrawal, 20 February 2026

The remediation moves the configuration that drives prefix advertisement out of the single authoritative database and into versioned snapshots that deploy the way binaries do, so a change that withdrew roughly 1,100 prefixes becomes a rollout we halt and revert in seconds instead of a database restore we reason about for hours.

The deleting call was well formed as far as any component could tell. A cleanup sub-task passed `pending_delete` as an untyped string carrying no value, and roughly 1,100 BYOIP prefixes were withdrawn along with their service bindings. An untyped string has no invalid member, so neither the client library nor the server had anything to reject. The first workstream gives these fields a stricter schema, which lets tooling decide whether a call is well formed before the call reaches the state that BGP reads.

Recovery cost tracked how far each deletion got, and the affected prefixes fell into three classes. Prefixes that were only withdrawn came back with a toggle in the customer dashboard. Prefixes withdrawn with some bindings removed recovered partially, and the remaining bindings needed our engineers. Prefixes withdrawn with every binding removed required a global configuration push to every edge machine, which is the slowest change we can make and the one we least want on the critical path of a single customer's restore.

The second workstream separates operational state from configured state, because today they share one database and that database is the only record of what production should look like. A customer configuration change and an internal operational action write to the same authoritative store, so there is no desired state to compare an actual state against, and recovery becomes a database-snapshot restore rather than a reconciliation. We will snapshot what the system reads from that database and applies to production, then roll those snapshots out progressively, gated by health metrics that stop the rollout when they move the wrong way. The previous known-good version stays loadable for one customer or for every customer.

This design blocks direct API updates for the duration of an incident, and we are choosing that. A customer who cannot change their prefix configuration for an hour is in a better position than a customer whose traffic is not being served, and the second failure is what happened on 20 February.

The third workstream is a circuit breaker on the rate and breadth of change. Monitoring will watch how many objects a deployment touches and how fast, including bursts of BGP prefix withdrawals and deletions, and halt snapshot deployment when either exceeds what normal operation produces. Signals from direct monitoring of customer services can trip the same breaker, which covers the case where the change looks ordinary in our own counters and the customer's traffic says otherwise. A breaker of this kind would have stopped the 20 February cleanup well short of 1,100 prefixes.

All three workstreams sit under Code Orange: Fail Small, which holds three commitments for any configuration change that propagates across the network. Every such change gets a controlled rollout. Break-glass procedures get dependency graphs with no cycles, so recovering from an outage never requires the system that is down. Each component gets defined behaviour under all of its failure modes, including the mode where the input is syntactically acceptable and semantically empty.

We will report progress on each workstream to customers as it ships, starting with the schema change, which is the smallest and closest to the specific defect.
