Twenty years of missing stacks

The default that costs us application frames on every profile today was set in 2004, on a machine that no longer exists, for reasons that were defensible on that machine and were never re-examined when the machine changed. %rbp is the x86-64 ABI's frame pointer, the register that holds the base of the current stack frame, and external profilers and debuggers -- Linux perf, eBPF -- walk a stack by following the chain of saved %rbp values from frame to frame, which is the mechanism that makes flame graphs possible at all. The ABI marks that use as optional. Compiled code is free to index into its frame off %rsp instead, which drops two instructions from each function's prologue and epilogue and hands one general-purpose register back to the allocator, and for two decades the compilers have taken that trade by default.

2004: a defensible change on i386

Roger Sayle, a gcc developer, patched the i386 backend so that 32-bit targets compiled as though -fomit-frame-pointer -ffixed-ebp had been passed on the command line. On i386 the register argument was not a rounding error: the allocator went from four general-purpose registers to five, or from six to seven if you count %si and %di, which is a 25% increase in the thing that i386 code was most starved of. Sayle gave two further reasons. He wanted to beat Intel's icc on benchmarks, which was a live competitive concern at the time, and he took the view that the debuggers of the day would be unharmed, since they supported other ways of walking a stack.

The extension is where the reasoning stopped applying and nobody noticed. The same default was carried across to x86-64, a target that already had more than a dozen general-purpose registers and therefore gained close to nothing from one more, and the benchmark argument that justified the change on a four-register machine was never re-run against the sixteen-register one.

Eric Schrock, then at Sun, objected in November 2004, and his objection reads today like a list of the things that were about to go wrong. On amd64, he wrote, a 17th general-purpose register opens up no new class of compiler optimization; all you avoid is a pushl/movl sequence that the hardware has long since learned to optimize; leaf routines never establish a frame at all, so a large fraction of the functions you would be saving instructions in were already paying nothing. Set against the cost in lost debuggability, he did not think the trade was worth making. His closing line named the failure mode precisely: the practice goes off the rails once people begin compiling /usr/bin without frame pointers. Linux then did exactly that, and not only /usr/bin -- /usr/lib and application code too.

What a broken chain actually costs

A stack walk that reaches a frame-pointer-less libc terminates there, and the trace comes back without the application frames above it, which is the part a profile is usually being taken to find. The effect on a flame graph is not subtle noise. Truncated stacks share no common prefix with the real ones, so they pile up together on the left edge of the graph as a single undifferentiated block: 15% of the samples in one example, 15% of your CPU time attributed to nothing. Off-CPU flame graphs come off worse still, because libc read and write and mutex calls are most of what an off-CPU profile contains by construction, which means the broken frames are concentrated in exactly the paths you are profiling for.

2014: putting the frames back, one runtime at a time

Joining Netflix in 2014 turned this from a known annoyance into a blocker, because Java had no frame pointer support at all and every application stack was broken, not 15% of them. The fix was a change to the JVM's c2 compiler to preserve the frame pointer; Oracle reworked that patch and shipped it as -XX:+PreserveFramePointer in JDK8u60, which is the flag people still set today, usually without knowing why it needs to exist.

libc came next, and it was the harder half, because a runtime flag can be flipped per-process while a system library has to be rebuilt and then shipped by somebody. The first version was a private libc built with frame pointers and run in production; the durable version came out of work with Canonical on a prebuilt libc6-prof. The sequencing is the point. Each of these is a separate negotiation with a separate owner, twenty and then ten years downstream of a patch whose stated justification -- four registers becoming five, and debuggers that could cope -- had already stopped being true of the target before the change reached it.
