Impact analysis

Every product described below failed for one reason: it called the core proxy, directly or through Workers KV, and the core proxy was returning errors. Workers KV sits one hop away because its front-end gateway routes requests through that proxy, so KV returned heavily elevated 5xx for the length of the incident, and each service reading from KV inherited KV's failure rate. At 13:04 we deployed a patch that let Workers KV bypass the core proxy. Error rates fell across KV and across everything downstream of it, including Access, from that minute onward. All times below are UTC.

Cloudflare Access failed authentication requests from the start of the incident until the rollback at 13:05. Two boundaries matter for your security review. Existing Access sessions kept working throughout, so users already inside an application were never logged out and never re-challenged. Every failed authentication terminated at an error page, which means no user reached a target application while authentication was broken; the failure mode was closed, not open. Logins that did succeed inside the window were logged correctly, so your audit trail for that period is complete and you can reconcile it against your SIEM without adjustment.

Access configuration updates attempted during the window either failed outright or propagated very slowly. We have since recovered all of them. If you pushed a policy, application, or group change during the incident and saw it either error or sit unapplied, check its current state now and confirm the recovered version is the one you intended, because a slow propagation and a failed write look identical from the dashboard.

The Dashboard lost availability across two separate windows with two separate causes. The first ran from 11:30 to 13:10 and ended when the Workers KV bypass took effect at 13:10; the Dashboard depends on Workers KV internally, and its login flow depends on Turnstile, which failed to load. Anyone holding an active session could keep working, and anyone without one could not log in at all. The second window ran from 14:40 to 15:30 and was not a relapse of the first. Restoring the feature file released a backlog of queued login attempts, those attempts arrived alongside client retries, and the combined load exceeded control plane capacity. Scaling control plane concurrency around 15:30 cleared it.

Email Security processed and delivered mail throughout, with degraded detection quality. The service lost access to an IP reputation source, which reduced spam-detection accuracy and suppressed some new-domain-age detections for the duration. No mail was dropped. Some Auto Move actions failed during the window and we have remediated them. Messages that would normally have been caught by reputation or domain-age signals may have landed in user inboxes, so we recommend re-scanning inbound mail from the window if your tenant handles high-value targets.

CDN response latency rose for a reason unrelated to cache or origin health. Our debugging and observability systems consumed large amounts of CPU enriching uncaught errors, and that enrichment work competed with request serving on the same hosts. The CDN kept serving traffic; the cost of describing the failure is what slowed it down.

Two checks are worth running against your own records. Compare your Access authentication logs for 11:30 to 13:05 against expected volume to size how many of your users hit the error page, and diff any Access configuration you changed on 18 November against what is live now.
