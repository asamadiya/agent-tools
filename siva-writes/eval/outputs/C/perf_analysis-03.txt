A filesystem nobody was using burned 38% of a fleet's CPU

A microservice team doing metrics ingestion updated their base OS image and then reported that ZFS was eating over 30% of their CPU capacity. The engineer they pulled in had worked on ZFS internals at Sun and did not believe the claim: unless you have badly misconfigured it, ZFS does not consume that much CPU, and the ways to misconfigure it that badly are a short and well-known list. He checked anyway, which is the only part of this story that was obvious in advance.

Atlas, the cloud-wide monitoring tool, showed 38% of CPU time in sys. That is unusual for Netflix cloud workloads, where the interesting time is normally in user, so whatever the team was seeing was at least real and at least in the kernel. The next step is where this diverges from the usual procedure. Instead of SSHing to an instance and running mpstat(1) and perf(1), he pulled a flame graph through Netflix's fetch tooling -- Vector then, FlameCommander later -- which takes about as long as loading a dashboard and does not require knowing which instance to log into first.

The flame graph showed two orange kernel towers, one on the left and one on the right, which is the shape you get when two threads are doing related work rather than one thread doing something pathological. The left tower was arc_reclaim_thread. The right tower entered spl_kmem_cache_reap_now(), another ZFS memory-freeing path, and the two were almost certainly contending on the same locks. Both towers are ZFS. At this point the team's claim looked correct and the ZFS engineer's prior looked wrong.

The Adaptive Replacement Cache is ZFS's main memory cache, and arc_reclaim_thread is the thread that keeps it inside its budget: it runs arc_adjust() to evict buffers and to maintain a free-memory threshold, waking periodically or when the system signals low memory. There is one known historical way to make that thread burn CPU, which is to set a tiny record size -- 512 bytes, say -- so that a modest amount of cached data becomes millions of separate buffers for the eviction walk to traverse. The default record size is 128 Kbytes. Nobody should be tuning below 8 Kbytes, and a metrics ingestion service has no reason to go near it.

The first theory was containers. A new infrastructure project was using ZFS to back containers, and container churn means filesystem churn, which would give arc_reclaim_thread a steady supply of buffers to tear down. The team said they were not using containers. Then, asked the more basic question, they said they were not using ZFS at all.

Two instances confirmed it. df -h showed no ZFS filesystems. mount showed none. zfs list showed none. That leaves the flame graph and the ground truth in direct contradiction, and the way out is /proc/spl/kstat/zfs/arcstats, which reports what ARC itself thinks it has done. Every counter read zero: hits 0, misses 0, all of them. ARC had never cached anything. It was still spending 38% of the machine's CPU deciding what to evict.

Reading the ZFS source and its change history closed it. A multilist performance feature had split the ARC's lists one per CPU, which is the standard fix for lock contention on a hot list, and the eviction path then has to pick which list to evict from. It picks at random. The random number came from get_random_bytes(), backed by extract_entropy() -- a cryptographically secure generator, which is roughly the most expensive way available to answer a question whose correct answer here is "any of them." Those two functions are exactly what the flame graph tops out in.

So the loop was: the kernel reports low system memory, which it will do on a busy instance whether or not ZFS is involved; ARC wakes arc_reclaim_thread; the thread pays for cryptographic entropy to select one of N per-CPU lists; the list has zero entries, because every list has zero entries; the thread finds nothing to evict and goes around again. Every element of that loop was doing its job. The cost only became visible because nothing was there to amortize it against.

It was filed as ZFS issue #6531. The first fix made arc_reclaim_thread bail out earlier when ZFS is unused, which removes the zero-work case but leaves the expensive RNG on the path that actually evicts. The useful generalization is not about ZFS. A per-CPU sharding optimization moved a cost from a contended lock into a random selection, and the selection was priced for a threat model that eviction does not have.
