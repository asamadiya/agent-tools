Diagnosis: the page cache

The memory numbers on the problem instance gave us the theory before any tracing tool did. `free -m` reported a 64,414 MB total with 15,421 MB used, 349 MB free, 48,643 MB in buff/cache, 48,409 MB available, and no swap configured, which is an entirely normal picture for a file-processing box -- the kernel has handed almost everything that is not resident process memory to the page cache, as it should. What made it interesting was the file sizes: the uploads that took hours were 100 Gbytes and the ones that took minutes were 40 Gbytes, and the page cache on this instance holds about 48 Gbytes. A 40-Gbyte file fits in 48 Gbytes of cache and a 100-Gbyte file does not, so if the service makes more than one pass over the file, the large case has to re-read from disk on every pass while the small case never does.

That is a theory about hit ratios, and `cachestat` measures hit ratios directly. It is an experimental tool, originally written against Ftrace and since ported to bcc/eBPF, and it is the only thing in the standard toolbox that will tell you what fraction of page cache lookups actually hit. During a 100-Gbyte upload it reported per-second hit ratios of 74.1%, 9.7%, 6.5%, 12.0%, 34.5%, 7.0%, and 11.1%, with misses climbing from 632 in the best second to 23,341 in the worst, BUFFERS_MB at 17 and CACHE_MB pinned at roughly 48,000. Ratios in the upper 90s are what a healthy workload looks like. Single-digit hit ratios with cache sitting at its ceiling are cache busting: the working set exceeds the cache, every miss becomes a disk read, and the upload runs at disk speed for as long as it runs.

The control test closed it. On a 32-Gbyte upload, `cachestat` showed a 100.0% hit ratio with zero misses in every second sampled, hits ranging from 33,424 to 65,158, BUFFERS_MB 41 and CACHE_MB around 33,680 -- the cache grew to the size of the file and stopped. `free -m` during that run showed 18,421 MB used, 11,218 MB free and 34,773 MB in buff/cache, so the instance still had 11 Gbytes of headroom it never needed. `iostat` showed almost no disk I/O for the duration. However many passes the code makes over a 32-Gbyte file, it makes them out of memory. The difference between the two runs is not a code path, a lock, or a network effect; it is whether the file fits.

Recommendations

The fast fix is a larger-memory instance, sized so that 100-Gbyte files fit in the page cache with room for the process itself. On this family that means moving well past 64 Gbytes, and the win should be close to the difference between the two runs above -- zero misses against tens of thousands per second. It costs money per instance-hour and it buys back nothing if file sizes keep growing, which they usually do.

The durable fix is in the application. The code is making multiple passes over a whole file that it assumes is cheap to re-read, and that assumption holds only below the cache ceiling. Rework it to process the file in parts, so that each part is read once and finished before the next one displaces it, and the workload stops depending on total file size at all. That is more work than resizing an instance and it is the change that survives the next customer who uploads 400 Gbytes.

One note on tooling. `cachestat` was the killer tool here and it is still experimental, written under real constraints: low overhead, and Ftrace function profiler only. At the LSFMMBPF 2019 keynote in Puerto Rico I argued in front of Linux mm engineers that these statistics are needed often enough to belong in /proc. They pointed out real difficulties in providing them properly. Page cache counters sit on hot paths, and instrumenting a hot path is never free.
