Cloudflare Dashboard and API outage, 12 September 2025

Between 17:57 and 19:12 UTC on 12 September 2025, the Cloudflare Dashboard was unavailable and much of the public API returned 5xx errors. Tenant Service, which evaluates authorization for every API request, was overwhelmed by request volume from the Dashboard; a request whose authorization cannot be evaluated fails, so the errors propagated to every API surface behind it. The Dashboard was the loudest casualty because it is itself an API client. Our control plane and data plane are strictly separated, and no network service -- proxying, caching, WAF, DNS resolution -- was affected. If you were not making configuration changes during that window, you almost certainly saw nothing. We are sorry for the time this cost the customers who were.

The trigger was a Dashboard bug we shipped at 16:32. A React useEffect hook issued the call to our /organizations endpoint, and its dependency array held an object that was recreated on every state or prop change. React compares dependencies by reference, so it read a fresh object on each render and re-ran the effect. A single Dashboard session therefore issued that API call many times per render pass, and each failure added retry traffic on top.

The load alone did not take the service down. At 17:50 we deployed a new version of the Tenant Service API. Seven minutes later, at 17:57, Tenant Service was saturated and Dashboard availability began to drop.

Our response made the incident worse before it made it better. We added pods to Tenant Service, which is a Go process running on Kubernetes across a subset of our datacenters, and by 18:17 the API had recovered to 98% availability. The Dashboard had not recovered at all. At 18:58 we shipped a change intended to remove the erroring codepaths, and API impact increased. At 19:01 we published a temporary global rate-limiting rule on the Tenant Service call path. At 19:12 we reverted the 18:58 change, and Dashboard availability returned to 100%.

Restarting Tenant Service turned recovery into a second load event. Every Dashboard session re-authenticated at once when the service came back, and the retry loop described above multiplied that herd instead of letting it drain. Each restart bought a smaller window of health than the last.

Two gaps made the incident longer than it needed to be. First, Argo Rollouts, which watches error rates during a deploy and rolls back automatically, has been adopted across much of our platform but not yet for Tenant Service. It would have reverted the 18:58 change without a human in the loop, and probably the 17:50 one as well. Second, our Tenant Service telemetry counts requests, not first attempts. Responders on the call could see request volume climbing and could not tell how much of it was new work and how much was the same failing calls coming back, which is the measurement that would have pointed at the Dashboard within minutes.

Here is what we are changing. We have fixed the dependency array in the Dashboard and are auditing our other useEffect-driven API calls for the same reference-identity mistake. We are onboarding Tenant Service to Argo Rollouts so that a bad version is withdrawn on its own error signal. We are adding retry labelling to Tenant Service telemetry so responders can separate retries from new requests on a dashboard rather than by inference. We are also giving Tenant Service standing capacity headroom and a permanent rate limit, so an abusive client degrades itself instead of every API caller.
