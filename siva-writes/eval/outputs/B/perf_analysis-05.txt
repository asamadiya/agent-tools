Uploads of 100-Gbyte files ran for hours while 40-Gbyte files finished in minutes, and that nonlinearity is the finding worth chasing. A 2.5x increase in file size bought roughly a 20x increase in wall time. Linear resource exhaustion -- a saturated NIC, a CPU-bound cipher, a throttled device -- does not produce that shape. Something changes state between 40 and 100 Gbytes. The service encrypts large files and ships them to S3, running on a 16-CPU AWS instance under kernel 4.4.0-1072-aws, December 2018.

Atlas, the cloud-wide monitoring tool, showed a paging spike over the slow window, specifically pageins, which count pages faulted in off disk. Plenty of healthy workloads generate pageins, and the instance was not swapping in any obvious way, so treat this as a direction to look rather than a diagnosis. It does agree with the size threshold: pageins rise when a working set stops fitting in memory.

We started from the 60-second checklist. Here is iostat -xz 1 during a large upload, device xvdb: r/s 734 to 750, rkB/s 91,656 to 92,152, avgrq-sz 246 to 250, avgqu-sz about 25, r_await 33 to 34 ms, %util pegged at 100. CPU over the same seconds ran about 14.8% user and 24 to 30% iowait. At 27% iowait across 16 CPUs, 4.3 CPUs' worth of capacity sat blocked in disk wait while user code burned 2.4.

Reads are the operations applications block on; writes often are not, because the page cache absorbs them and flushes later. A 33 ms read wait is high for an EBS volume. Check where it comes from before blaming the device: queue depth divided by completion rate gives 25 / 740 = 33.8 ms, which reproduces the measured 33 to 34 ms to within the rounding of the inputs. The latency is the queue. The device is servicing requests at the rate it always does, and 25 of them are stacked up waiting their turn.

That also disarms %util. At 100% the column means the device had at least one request outstanding during every sampling interval, which for a virtual, network-attached, internally parallel block device is a statement about continuous demand and not about a hardware limit being reached.

Dividing rkB/s by r/s puts the average read at 123 to 125 Kbytes. That is large, and large reads at a steady 92 Mbytes/s are the signature of sequential streaming, not of scattered metadata access. Note the arithmetic on the complaint: one pass over 100 Gbytes at 92 Mbytes/s costs 1,113 seconds, about 19 minutes. Hours means the file is being read several times over, or the stream stalls for long stretches, or both.

Per-second averages can hide device-level outliers, so we ran biolatency -m from bcc, an eBPF histogram of block I/O completion times. Of 10,267 sampled I/O, 8,139 landed in the 32-63 ms bucket and 1,620 in 16-31 ms; 96.8% of all I/O fell between 16 and 127 ms. The tail reached 512-1023 ms, but only 154 I/O, 1.5% of the sample, exceeded 256 ms. No bimodality, no cliff, no cluster of multi-second completions. The distribution is centered exactly where Little's law said queueing would put it.

bitesize from bcc, which buckets I/O size by process, attributed 1,682 I/O to java in the 128-255 Kbyte bucket with only tens in every other bucket. One process, one size class, matching the iostat average.

Four tools agree, and none of them accuses the storage device. The workload is issuing large sequential reads faster than the volume will retire them, and the queue it builds accounts for the full observed latency. The open question is why a file this size generates disk reads at all, given that 40-Gbyte files apparently do not. Run the upload against files stepped from 40 to 100 Gbytes and watch where pageins begin; the size at which they appear should name the memory boundary being crossed.
