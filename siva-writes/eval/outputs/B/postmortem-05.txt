Remediation

On 20 February 2026 a cleanup sub-task passed pending_delete with no value, the API accepted the call, and roughly 1,100 BYOIP prefixes and their service bindings were deleted. Three workstreams follow from that failure, and all three sit under a wider program described at the end.

Typed API schemas. The sub-task sent pending_delete as an untyped string, so neither the client library nor the server could reason about what the value meant or whether an empty one was legal. A stricter schema moves that judgement into the interface: the call either matches a declared shape or it is rejected before it reaches the deletion path. Tooling, tests and the server can all check the same contract, and an empty value in a field that governs deletion stops being a request we are willing to execute.

Separating operational state from configured state. Today a customer editing a prefix in the dashboard and an engineer running an operational action write to the same authoritative database, which is why recovery meant restoring from database snapshots. We are changing what production reads. The system will snapshot what it reads from the database and applies to the edge, then roll those snapshots out the way we ship binaries, gated by health metrics that halt a bad rollout in place. A revert then becomes a version change, applied to one customer or to every customer, in seconds instead of hours. The tradeoff is explicit: while a snapshot rollout is halted, customers cannot push configuration changes through the API, and their existing traffic keeps being served. We would take that exchange again -- a configuration freeze is an inconvenience, a withdrawn prefix is an outage.

A circuit breaker on rate and breadth of change. Monitoring will watch how much is changing and how widely, so a burst of BGP prefix withdrawals or a deletion count far outside the normal band halts snapshot deployment before it propagates. Signals from direct monitoring of customer services can trip the same breaker, which means a degradation we see from the outside can stop a rollout even when the change itself looks well formed. The breaker does not need to diagnose the fault. It needs to stop the spread.

Recovery cost scaled with how far the deletion got, and that shaped the priorities above. Three classes appeared during the incident. A prefix that was only withdrawn came back with a dashboard toggle. A prefix that was withdrawn and had lost some of its service bindings came back partially, with the missing bindings rebuilt by hand. A prefix that was withdrawn and had lost all of its bindings required a global configuration push to every edge machine, which is the slowest recovery path we have and the reason the tail of this incident ran as long as it did.

These workstreams belong to Code Orange: Fail Small, the program we have prioritized above feature work. It has three buckets. Any configuration change that propagates across the network gets a controlled rollout, with the same staging, health gating and revert that code changes get. Break-glass procedures must work without circular dependencies, so recovering from an outage never requires a system that the outage has taken down. Every component must have defined behaviour under all failure modes, including the modes where its inputs are missing or empty, which is exactly the case that produced this incident. We will report progress on each bucket as the work lands.
