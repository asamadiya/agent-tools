Root cause

A routine database permissions change, not an attack, took down our network on 18 November 2025. At 11:05 UTC we deployed a change to a ClickHouse database cluster that let query accounts see metadata for the tables underlying the r0 database instead of only the default database. The change was correct in itself and had nothing to do with bot management. It was consumed, unintentionally, by a query nobody had revisited in years.

The Bot Management feature file is regenerated every five minutes by a query over system.columns. That query filtered on table name and not on database name. Before 11:05 the filter was adequate, because the querying account could see only one database and that implicit scoping did the work the WHERE clause did not. After 11:05 the same account could see the same table in two databases, and every column came back twice. The generated file carried more than double its usual number of feature rows.

Our proxy will not load more than 200 features from that file. The bots module preallocates memory for the feature set, and 200 was chosen as more than three times the roughly 60 features the bot-scoring model actually uses at runtime -- headroom we believed generous, and that no file had ever approached. The doubled file crossed it. In the FL2 proxy engine, the code that loads the file called unwrap on a Result that could now be Err, and thread fl2_worker_thread panicked. A panicked worker cannot serve the request it was holding, and the request became an HTTP 5xx.

The network then failed and recovered on a five-minute cycle. The permissions change rolled out gradually across ClickHouse nodes, and each regeneration read whichever node it reached: a node still carrying the old permissions produced a good file, an updated node produced a bad one. A good file restored service, and the next bad one took it away again. An oscillation of that shape looks more like an attack than like a bad deploy, and for a while we read it that way.

Customers on the two proxy paths saw two different failures. FL2 customers saw 5xx errors, which were loud and unambiguous. FL1 customers saw no errors at all; their traffic was scored, but every request received a bot score of zero. Any customer whose rules block on a low bot score blocked real users and had nothing in their logs to explain it. The silent failure is the worse of the two to have shipped.

Two things lengthened the diagnosis. Cloudflare's status page is hosted entirely outside our infrastructure and shares no dependency with it, and it went down at the same time for unrelated reasons. We read the coincidence as evidence: an Aisuru-style DDoS large enough to hit both our edge and an independent host was a coherent story, and we spent time on it. There was no attack.

Impact began at 11:28. Automated detection fired at 11:31, three minutes later, and we opened an incident call at 11:35. At 13:05 we bypassed Workers KV and Access from the affected path, which restored those products for their customers. At 14:24 we stopped propagation of the bad feature file and forced a known-good version. Core traffic was normal at 14:30, and every downstream service was clear at 17:06. Between 11:28 and 14:30, just under three hours, a large share of requests through our network failed. This is our worst outage since 2019.

The permissions change was the trigger, not the root cause. The root cause is that a query with an under-specified filter fed an unvalidated file into a hot path, and the hot path answered an unexpected input by panicking instead of rejecting the file and continuing to serve with the last good one. A ceiling of 200 features is a reasonable guard; crashing when a file exceeds it is not. We generate that file ourselves, and we treated it as trusted for exactly that reason -- the same mistake as trusting any input because of where it came from rather than because it was checked. We are now validating every internally generated configuration file the proxy consumes, on the same terms as user input, and we are removing the panic paths that let a malformed one take a worker thread down.
