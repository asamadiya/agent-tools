Root cause

A database permissions change made a metadata query return duplicate rows, and those duplicates doubled the size of a configuration file that our proxy refuses to load past a fixed limit. The failure was not an attack and not a capacity problem. All times below are UTC on 18 November 2025.

At 11:05 we deployed a permissions change on a ClickHouse database cluster. The change let users read metadata for the underlying tables in the r0 database, not only for the default database they previously saw. That is the behaviour we wanted. One query in our Bot Management pipeline had been written against the narrower view.

Bot Management regenerates a feature file every five minutes from a query over system.columns. That query filters on table name and does not filter on database name. Before 11:05 the query saw one database and returned one row per column. After 11:05 it saw the same columns in both the default and r0 databases, and it returned each feature twice. The generated file carried more than double the feature rows it had carried at 11:00.

The proxy's bots module preallocates memory for that file and will not load more than 200 features from it. The bot-scoring model uses roughly 60 features at runtime, so the file had sat at less than a third of the limit for its entire life and nobody had watched the margin. The doubled file crossed 200. In our FL2 Rust proxy path, the load returned an Err that the calling code unwrapped, the thread named fl2_worker_thread panicked, and every request that thread was handling returned HTTP 5xx.

Two things made the outage harder to read than a single bad deploy would have been. First, the ClickHouse permissions change rolled out gradually across nodes, so for about three hours the five-minute regeneration job hit sometimes a patched node and sometimes an unpatched one. A good file and a bad file alternated. The network recovered and failed again on that cadence, which is the signature we associate with an attacker adjusting load, not with a config regression. Second, our status page is hosted independently of our own infrastructure and went down at the same time for unrelated reasons. Responders reasonably suspected a large volumetric attack of the Aisuru kind and spent early minutes looking in that direction.

Customers saw one of two distinct failures depending on which proxy version served them. FL2 customers saw 5xx directly. FL1 customers saw no errors at all, and instead received a bot score of 0 on every request, because the scoring path fell through without features. Any customer with a rule that blocks on low bot score therefore blocked legitimate traffic and saw no error in their logs to explain it. If you run such a rule, the false positives in your traffic between 11:28 and 14:30 came from us.

Impact began at 11:28. Automated detection fired at 11:31 and we opened an incident call at 11:35. At 13:05 we bypassed Workers KV and Access from the affected path, which restored those products ahead of the rest. At 14:24 we stopped propagation of the bad feature file, and core traffic was normal at 14:30. Downstream services finished draining and we declared all clear at 17:06. Core impact ran 3 hours 2 minutes and the full incident ran 5 hours 38 minutes, our worst outage since 2019.

Three specific engineering faults produced this, and each one is independently sufficient to have prevented it. The query trusted an implicit database scope that a permissions grant was free to widen, and it should have filtered on database name. The 200-feature ceiling was a silent hard limit on a file generated by a separate system on a five-minute loop, with no alert on the gap between 60 and 200. And a file we generate ourselves and ship into the request path was treated as trusted input, so a parse failure reached an unwrap in FL2 rather than a rejection of the new file and continued service on the last known-good one. Look at your own configuration pipelines for the same shape: a generated artifact, a size bound in the consumer, and no check that the producer still respects it.
