How to reason about coding-agent capability

A coding agent's capability is a property of the loop we build around the model, not a property of the model, and our team's leverage is almost entirely in the loop. This document sets out the reasoning, borrowed from an analog circuit, and what it implies for where we spend engineering time.

Start with a circuit that extracts a good answer from a bad part. Take an operational amplifier and an analog multiplier IC, say the long-obsolete MC1495. Wire the amplifier's output through the multiplier back to one of its inputs, so that input sees the output multiplied by itself. Apply a voltage on the left and read the square root of that voltage on the right. Build it and measure it.

The mechanism is the feedback, not the parts. An opamp drives its two inputs to equality. When one input carries the output squared and the other carries the input voltage, the only settling point is the output equal to the square root of the input. The multiplier's own gain error and offset are divided down by the amplifier's open-loop gain, which is why a mediocre multiplier inside the loop yields a square root far more accurate than the multiplier is on its own. A component inside a feedback loop behaves very differently from the same component open-loop.

An AI agent has this shape. The LLM is the imprecise component, useful open-loop and wrong in ways we can enumerate: invented APIs, off-by-one edits, plausible code that does not compile. The compiler, the test suite, and the runtime are the feedback path, and they measure the error the model cannot see in itself. Developer tooling has moved over roughly two years from open-loop autocomplete in the IDE to agents, which is the same move: the build-test-iterate loop relocated from the human into the machine. The model did not stop hallucinating APIs. The loop now rejects them before a human reads them.

Expect the capability profile to stay jagged, because it has been jagged for 85 years. Computers have been super-human since Marian Rejewski's cryptanalytic work in the 1930s, and a current MacBook adds 64-bit numbers about 100,000,000,000 times faster than a person does. Across those nine decades the pattern never resolved: vastly super-human in some areas, well short of human in others. Agents today build meaningful, correct software quickly and at very low cost, and they are super-human on some coding tasks. "Is the agent better than an engineer" has no answer, and we should stop asking it.

Evaluate every proposed change by what it does to the loop. Three properties govern closed-loop quality: the sharpness of the error signal, the latency of one iteration, and the breadth of what the loop can observe. That makes test coverage, deterministic and fast builds, type and lint signal, and observable runtime state our primary investments, and it makes per-iteration wall-clock a first-class metric. A better model improves the open-loop term, which the loop then divides. A better loop divides harder.
