Slow 100-Gbyte uploads: the disk is not slow, the queue is 25 deep

The 33 ms read latency on this upload path is queueing produced by the workload itself, not a slow device: xvdb is serving 740 reads per second at 100% utilization, and the only reason any single read waits 33 ms is that roughly 25 other reads are already in front of it.

Start with iostat -xz 1 taken during a large upload. Device xvdb reports r/s between 734 and 750, rkB/s between 91,656 and 92,152, avgrq-sz 246 to 250 sectors, avgqu-sz about 25, r_await 33 to 34 ms, and %util pinned at 100. CPU over the same seconds is about 14.8% user against 24 to 30% iowait. Reads are what matters here, because an application blocks on a read and frequently does not block on a write -- write-back caching lets the kernel acknowledge the write and flush it later -- so the 33 ms figure is latency that the uploader actually pays.

Little's law accounts for the entire 33 ms without appealing to anything wrong with the hardware. Queue depth equals arrival rate times residence time, and 740 reads per second times 0.0335 seconds gives 24.8 outstanding reads, which is the avgqu-sz of about 25 that iostat already printed. Run it the other way: at 100% utilization and 740 completions per second the device spends about 1.35 ms of service on each read, and 25 times 1.35 ms is 34 ms. The wait tracks the depth of the queue and not the speed of the device, and dividing 92,000 kBytes per second by 740 reads per second says each of those reads is about 125 Kbytes, a large I/O and the size a device is most efficient at serving.

Per-second averages can hide device-level outliers, so the next tool is biolatency -m from bcc, an eBPF histogram of block I/O latency. Across 10,267 sampled I/O, 8,139 land in the 32-63 ms bucket and 1,620 in 16-31 ms, which puts 95% of the sample in the 16-63 ms range that the iostat average already described. The tail is thin: 176 at 64-127 ms, 95 at 128-255 ms, 61 at 256-511 ms, and 93 at 512-1023 ms, together 2.2% of the sample. A device with a failing spindle, a firmware stall, or a noisy neighbour produces a bimodal histogram with a fat isolated slow mode; this one is a single mode sitting exactly where a 25-deep queue of 1.35 ms operations would put it.

bitesize from bcc rules out a size anomaly hiding inside that average. The issuing process is java, and 1,682 of its I/O fall in the 128-255 Kbyte bucket with only tens of operations in every other bucket. There is no population of small scattered reads inflating the count, and the size distribution agrees with the 125 Kbyte figure computed from iostat, which means two independent instruments now say the same thing about the request stream.

The remaining question is why a 100-Gbyte file generates this read stream when a 40-Gbyte file finishes in minutes on the same 16-CPU instance. The Atlas pageins spike is the hint rather than the proof -- pageins count pages faulted in from disk and plenty of healthy workloads generate them -- but a workload that runs in minutes below some size and hours above it, while the device shows nothing but honest queueing, is the shape of a residency cliff: below the threshold the file the service encrypts stays resident in page cache, above it the encrypt-and-ship pass reads back from disk. The 40-to-100-Gbyte gap brackets where that threshold sits on this instance, and nothing measured so far pins it more tightly than that.

Stop investigating EBS and start investigating the uploader's access pattern. The device is delivering 92 Mbytes per second in 125 Kbyte reads at full utilization, which is the throughput it is entitled to, and no storage-side change alters a latency that is 25 times the service time by construction. Measure the resident set of the encryption pass against instance memory, and count how many times each byte of a 100-Gbyte file is read.
