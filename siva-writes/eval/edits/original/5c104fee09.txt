Chasing a 30% write-latency regression across a distribution upgrade

We moved a Cassandra cluster from CentOS to Ubuntu as part of a fleet-wide migration and write latency rose by over 30%. Basic instance stats put over 30% more CPU consumption behind it, which is a useful starting point: a latency regression with a matching CPU regression is a regression you can profile, and not one you have to chase through the network or through disk. The instances are EC2 Xen guests, same instance type on both sides, same Cassandra version.

The first suspect is a rogue Ubuntu service, because a distribution upgrade changes the set of things running on the box far more than it changes the application. top(1) killed that suspect quickly: the only process consuming meaningful CPU was Cassandra's JVM. That is not a complete answer, since top samples on an interval and a storm of short-lived processes can burn real CPU without ever appearing in a single sample. execsnoop(8), the Ftrace version at the time, traces execs as they happen and showed nothing -- no periodic shell-outs, no agent restarting itself in a loop. Whatever the extra CPU was, Cassandra itself was on-CPU for it.

We collected CPU flame graphs on one CentOS instance and one Ubuntu instance in parallel. Running them at the same wall-clock time matters more than it sounds like it should, because the write mix a Cassandra node sees varies with time of day, and a profile taken an hour later is a profile of a different workload.

The Java stacks were broken on both instances, which is expected for that era -- this was before -XX:+PreserveFramePointer, so the JVM's frame pointer omission left us with one or two green frames where a tower of Java methods should have been. The breakage turned out to be useful. Broken stacks merged every call site of os::javaTimeMillis() into one block instead of scattering it across dozens of thin, individually unremarkable stacks. That block was 30.14% of the Ubuntu flame graph on its own, sitting in the middle where it was impossible to miss, and searching the whole graph brought the total to 32.1%.

A third of on-CPU samples spent fetching the time is a strong match to a 30% CPU increase, but it is a match and not a proof. The flame graph gives no counterfactual: we know the Ubuntu instance spends 32.1% of its sampled on-CPU time there, and the comparison that closes the argument is the same number on CentOS, measured the same way, at the same hour.

The mechanism under that block is specific. os::javaTimeMillis() calls gettimeofday(2), and above gettimeofday on the Ubuntu profile sit tracesys() and syscall_trace_enter/exit -- the kernel's syscall tracing slow path. Cassandra calls for the time constantly, on essentially every write, and a call that should resolve in user space is instead taking a full syscall entry with tracing overhead stacked on top.

That leaves two theories. (A) Syscall tracing is enabled on Ubuntu and not on CentOS, by auditing or by apparmor, which would tax every syscall the JVM makes and only show up loudly on the syscall the JVM makes most. (B) Fetching the time is simply slower on Ubuntu, through a library change or a kernel and clocksource change, and the tracing frames are incidental. The relative widths of the frames favored A: the tracing frames were wide enough that they looked like the cost rather than a thin wrapper around it.

The Ubuntu graph complicates that reading. It showed a vDSO frame with the syscall still above it, which is not what a working vDSO looks like -- the whole point of the vDSO path is that gettimeofday returns without entering the kernel. Xen pvclock did not support vDSO at the time, so the fast path was entered and fell through to a real syscall. That is evidence for B living inside a profile whose frame widths favor A, and both can be true at once: the fall-through creates the syscalls and tracing makes each one expensive.

One caveat bounds every number above. The profile used perf(1) with software cpu-clock soft interrupts, not hardware NMI sampling, because these are Xen guests and PMU-based sampling was not available to us. Software sampling cannot fire with interrupts disabled, so kernel paths that run with interrupts off are undersampled or invisible, and all time spent in the hypervisor is invisible outright. 32.1% is a share of what the profiler can see. The true share of wall-clock time in the time path could be higher or lower, and the syscall entry path is exactly the kind of code that a cpu-clock profile is worst at measuring.

Nobody on the team had hit this, and searching for os::javaTimeMillis together with clocksource, tracesys, Ubuntu, EC2, and Xen returned nothing. The next steps are cheap and each one separates A from B. Disable auditd and apparmor on a single Ubuntu instance and re-profile. Time a tight gettimeofday(2) loop in C on both distributions, which removes the JVM from the question entirely. Read /sys/devices/system/clocksource/clocksource0/current_clocksource on both, since a clocksource that cannot be read from the vDSO forces the syscall no matter what the tracing configuration says.
