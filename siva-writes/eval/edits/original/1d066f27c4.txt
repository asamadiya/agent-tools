Frame pointers on x86-64: a default measured on the wrong target

Twenty years of truncated stack traces on x86-64 come from a compiler default that was justified by a register-pressure measurement on i386 and then carried, unchanged and unremeasured, to a target where the register it frees is the seventeenth.

The register in question is %rbp, which the x86-64 ABI names as the frame pointer: it holds the base of the current stack frame, and each function's prologue pushes the caller's value and sets its own, two instructions, with a matching pop on the way out. External profilers and debuggers -- Linux perf, eBPF -- walk a stack by chasing that chain of saved %rbp values from frame to frame, which is the mechanism behind every flame graph you have ever looked at. The ABI marks the use as optional. Code can index into its frame off %rsp instead, which deletes those two instructions and hands %rbp back to the register allocator as a general-purpose register.

On i386, handing that register back was worth having. Roger Sayle patched the gcc i386 backend in 2004 so 32-bit targets compiled as though -fomit-frame-pointer -ffixed-ebp had been passed, and on a machine with four usable general-purpose registers the patch made it five, or six to seven if you count %si and %di. A 25% increase in the allocator's working set changes which values live in registers across a loop body and which spill to memory, which is a different class of generated code and not a shaved instruction. Sayle gave two further reasons: he wanted to beat Intel's icc on benchmarks, and he judged that the debuggers of the day would be unharmed, since they already supported other ways of walking a stack.

The same default was then applied to x86-64, where the arithmetic does not survive the change of target. Eric Schrock, then at Sun, objected in November 2004 and made the argument quantitatively: amd64 already had more than a dozen general-purpose registers, and a seventeenth opens no new class of compiler optimization, because at that width the allocator was not the binding constraint. What remains is the pushl/movl pair, which the hardware has long since optimized, and leaf routines -- the functions most likely to be hot -- never establish a frame at all, so they pay nothing either way. Schrock's closing line was that the practice goes off the rails once people begin compiling /usr/bin without frame pointers. Linux then compiled /usr/bin, /usr/lib and application code that way.

What makes the cost large is that the frame pointer is a property of a whole call path, not of a function. A stack walk stops at the first frame that did not set %rbp, and everything below that point in the chain is lost, including frames compiled with the pointer intact. libc sits on nearly every interesting path, so a walk that reaches libc returns without the application frames above it. In a flame graph those truncated traces do not scatter -- they all bear the same short prefix, so they merge into one block against the left edge, 15% of the samples in one example. The 15% is not the fraction of time you lost visibility into; it is the fraction of samples whose attribution collapsed into a single uninformative column.

Off-CPU flame graphs come off worse, because libc read and write calls and mutex operations are most of what an off-CPU profile contains by construction. The exact frames that terminate the walk are the frames the profile exists to explain.

Repairing this took a decade of per-runtime work, which is the measure of how expensive the default was. Java had no frame pointer support at all in 2014, which broke every application stack on a JVM; a c2 compiler fix written at Netflix was reworked by Oracle and shipped as -XX:+PreserveFramePointer in JDK8u60. libc came next: a private build with frame pointers for production first, then a prebuilt libc6-prof produced with Canonical. Each of those is one runtime and one distribution, and the reason each had to be done separately is the same path property above. A frame-pointer JVM above a frame-pointer-less libc still truncates.

Measure the trade on the target you ship on, with the register count that target actually has. Compile your hot binary both ways and compare cycles; on x86-64 the difference is usually within noise for anything that is not a tight leaf-heavy loop, which is the regime Schrock described in 2004. Then price the other side: run a profile against an unmodified libc and against libc6-prof, and count the fraction of samples that terminate before reaching application code. If that fraction is near 15%, the defaults are costing you attribution on one sample in seven, and the recovery is a rebuild with -fno-omit-frame-pointer plus -XX:+PreserveFramePointer for any JVM in the path.
