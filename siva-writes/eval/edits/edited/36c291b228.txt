Root cause: a database permissions change doubled a generated configuration file past a hard limit in our proxy

A permissions change we deployed to a ClickHouse database cluster at 11:05 UTC on 18 November 2025 caused a query to return every Bot Management feature row twice, and the doubled file crossed a 200-feature limit compiled into our proxy, which panicked and returned HTTP 5xx. All times below are UTC.

The query that builds the Bot Management feature file reads column metadata from `system.columns` and filters on table name without filtering on database name. Before 11:05, the account running that query could see metadata only for tables in the `default` database, so each column of the underlying table appeared in the result exactly once. The 11:05 change granted users visibility into metadata for the underlying tables in the `r0` database, where the same table also exists. Every matching column then appeared twice, once for `default` and once for `r0`, and the file regeneration job, which runs every five minutes, wrote a file with more than double its usual number of feature rows.

The proxy's bots module refuses to load more than 200 features from that file, and the doubled file carried more than 200. The limit exists because the module preallocates memory for the feature set at startup. We chose 200 against a bot-scoring model that uses about 60 features at runtime, which is more than triple the observed requirement, and no configuration we had ever shipped came close to it. A limit never approached is a limit never exercised.

Crossing the limit produced an `Err` that our FL2 proxy code unwrapped instead of handling, and the `fl2_worker_thread` panicked. The panic terminated request processing, and the customer saw a 5xx. We had treated this file as trusted because we generate it ourselves, and it is generated by a query whose output shape depends on database permissions we change independently of the proxy. The file is an input, and our code did not validate it like one.

The file alternated between good and bad every five minutes, because the ClickHouse permissions change rolled out gradually across nodes. Whichever node served the regeneration query determined whether that generation of the file carried the duplicates. Our network therefore failed, recovered, and failed again on a five-minute cycle for roughly two hours. That signature does not look like a bad deploy. It looks like an attacker adapting, and our independently hosted status page went down during the same window for unrelated reasons, which sustained a working hypothesis of an Aisuru-style DDoS well past the point where it should have been dropped.

Customers on FL1 saw no errors and worse data. The older proxy path did not panic on the oversized file; it scored all traffic as `bot=0`. Any customer with a rule blocking on bot score was blocking human traffic for the duration, and saw a clean 200-response error rate while doing it. We count this as impact equal to the 5xx, and it was slower to detect, because nothing in our own error metrics moves when scoring silently returns a constant.

The timeline from first impact to all clear was 6 hours 1 minute. Impact began at 11:28, automated detection fired at 11:31, three minutes later, and we opened an incident call at 11:35. We bypassed Workers KV and Access at 13:05, stopped propagation of the bad file at 14:24, and core traffic was normal at 14:30. Remaining services were restored at 17:06. This is our worst outage since 2019, and the first since then in which core traffic stopped flowing.

Three changes follow from this, and the first two are the ones that would have prevented the outage rather than shortened it. We are making the proxy treat every internally generated configuration file as untrusted input: bounded, validated on load, and failing to the last known good version instead of panicking the worker thread. We are eliminating unwraps on `Err` in the request path of FL2, which is the specific construct that converted a bad file into a dropped request. We are adding global kill switches for feature-file consumers, so the five-minute regeneration loop can be stopped from one place while the source query is fixed. The query itself now filters on database name.
