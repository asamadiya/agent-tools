Uploads got 2.5x bigger and got two orders of magnitude slower
==============================================================

The most informative number in the original report arrived before anyone ran a
tool. A service that encrypts large files and ships them to S3, running on a
16-CPU AWS instance on kernel 4.4.0-1072-aws, finishes files up to 40 Gbytes in
minutes and takes hours on files of roughly 100 Gbytes. Going from 40 to 100
Gbytes multiplies the bytes by 2.5 and multiplies the wall clock by something
closer to 100. A cliff that sharp between two sizes says a resource ran out
somewhere between them. Atlas showed a pageins spike over the same window.
Pageins count pages faulted in off disk and plenty of healthy workloads generate
them, so that is an arrow and not a verdict.

Start with the 60-second checklist. `iostat -xz 1` during a large upload, device
xvdb: r/s 734 to 750, rkB/s 91,656 to 92,152, avgrq-sz 246 to 250, avgqu-sz about
25, r_await 33 to 34 ms, %util pegged at 100. Divide rkB/s by r/s and each read is
about 124 Kbytes, which agrees with avgrq-sz at 512 bytes per sector. The device
is delivering roughly 92 Mbytes/s of reads in 128-Kbyte units, and the writes are
not interesting here because applications block on reads while write-back caching
usually lets them walk away from writes.

A 33 ms read wait looks alarming and is not evidence of a slow device. Apply
Little's law to the queue: 25 outstanding requests divided by 742 completions per
second is 33.7 ms, which reproduces r_await to the digit. Every millisecond of
that wait is accounted for by the 25 requests already in front. Per-I/O service
time is 1/742 s, about 1.3 ms, which is ordinary for network-attached storage
doing large reads. %util at 100 means the queue was never empty during the
sampling interval, and on a device that services requests concurrently that is a
statement about the submitter, not about the disk.

The CPU numbers point the same way. About 14.8% user across 16 CPUs is 2.4 cores
busy, and encryption is the kind of work that should saturate cores if it were
the bottleneck. Iowait sat at 24 to 30%. The job is waiting on storage with most
of the machine idle.

Per-second averages can hide device-level outliers, so the next tool was
`biolatency -m` from bcc, an eBPF histogram of block I/O latency. Buckets: 83 I/O
at 0-1 ms, 1,620 at 16-31 ms, 8,139 at 32-63 ms, 176 at 64-127 ms, 95 at 128-255
ms, 61 at 256-511 ms, 93 at 512-1023 ms. That is 9,935 of 10,267 samples, 96.8%,
landing between 16 and 127 ms, with 0.9% stretching past half a second. The
distribution has the shape queueing produces: a dense body sitting where 25-deep
queueing puts it and a thin tail from the moments the queue ran deeper. Nothing
here is a device that occasionally stalls for a second while otherwise behaving.
The histogram agrees with iostat and adds no new suspect.

`bitesize` next, to check whether the request sizes hide anything anomalous: 1,682
I/O from process `java` in the 128-255 Kbyte bucket and only tens in every other
bucket. One process is issuing essentially one size of read. There is no
small-random-I/O pathology tucked underneath the large-I/O average, which is the
usual reason to look.

All three tools describe the same well-behaved storage workload, which is why the
arithmetic on the file itself is the real finding. Encrypting a file and shipping
it requires reading it once. Reading 100 Gbytes at 92 Mbytes/s takes 1,087
seconds, about 18 minutes, and these uploads run for hours. The device is
therefore handing the application the file several times over. Put that beside the
pageins spike and the cliff between 40 and 100 Gbytes and one hypothesis covers
all three observations: the smaller file fits in page cache and the larger one
does not, so pages get evicted and re-read. A 16-CPU AWS instance of that
generation carries 64 Gbytes of memory, which sits exactly between the fast size
and the slow one, though the ticket never recorded the instance type. The next
question is which code path issues those reads and at what offsets.
