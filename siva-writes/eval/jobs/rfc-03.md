Raw material for the version-skew section of the in-place pod resize KEP. Timeline: the CRI changes merged in v1.25 so runtimes could implement support; containerd added support in 1.6.9. Older clients that do not know the ResizePolicy fields send them as nil, and the API server copies the non-nil values from the old pod forward. The skew problem: before v1.31, with InPlacePodVerticalScaling off, the kubelet read a resource mutation as a change to the container definition and restarted the container with the new values, which can over-subscribe the node. From v1.31 the kubelet no longer treats a resource change as a definition change and does not restart; the new value then takes effect only if the container restarts for some unrelated reason, so the change is nondeterministic and never reflected in the API. Both outcomes are bad, so the API server must reject a resize when the kubelet handling that pod lacks the feature. There is no direct signal, so the proxy is .status.containerStatuses[*].resources, which the kubelet sets on running containers if and only if the feature is enabled; note it is set to an empty {} even when the container declares no requests. Decision logic: feature gate off means reject; otherwise look at the first running container and allow only if its status resources are non-nil; with no running containers, allow. An unscheduled pod may be resized, with the new values used at scheduling and start. A scheduled pod with no running containers gives no signal, so resize is allowed and the node may end up over-provisioned. A race exists where a resize on a non-running container is admitted while the kubelet starts it: before v1.31 the container restarts with the new values, after v1.31 it keeps the old ones.
