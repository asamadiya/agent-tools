Raw material for a Kubernetes enhancement proposal on in-place pod resource updates. Today Pod.Spec.Containers[i].Resources is immutable, so any change to CPU or memory requests or limits forces the pod to be recreated. Three things drive a change: load rose and the allocation is short; load fell and the allocation sits idle; the values were simply set wrong. Stateless replicas usually survive recreation; low-replica services, stateful workloads and batch jobs pay in availability or cost. Core idea: the spec resources become desired state, and PodStatus is extended to report the resources actually applied. Three CRI gaps also need fixing: UpdateContainerResources takes a Linux-shaped resources parameter that does not fit Windows or future runtimes; there is no CRI call letting kubelet read back the CPU and memory limits a runtime has applied; and the behavior expected of a runtime handling a resource update is not documented. Goals: resize without necessarily restarting the container; let whoever initiated the resize (user, VPA, StatefulSet, JobController) choose what happens when in-place is impossible; let users mark which containers are safe to resize. Non-goals: QoS class change, non-restartable init containers, evicting lower-priority pods to make room, resource types other than CPU and memory, CPU/memory manager policies other than 'None', and resolving scheduler races.
