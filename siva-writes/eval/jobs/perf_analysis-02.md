Follow-on to a 2014 Netflix investigation where a Cassandra cluster on Ubuntu/EC2-Xen was burning about a third of its CPU inside os::javaTimeMillis(). No existing microbenchmark for that call existed, so one was written: TimeBench.java loops 100,000,000 times calling System.currentTimeMillis(), with a comparison against 87362 and a println inside the loop so the compiler will not optimize the loop away (which slows the test slightly). Run under shell time(1). CentOS: real 0m12.989s, user 0m3.368s, sys 0m18.561s. Ubuntu: real 1m8.300s, user 0m38.337s, sys 0m29.875s. Per-call cost is about 0.13 us on CentOS and 0.68 us on Ubuntu, Ubuntu 5x slower. A C version calling gettimeofday(2) directly, compiled -O0 to keep the loop, gave similar results; short benchmarks like this can be disassembled to confirm the compiler did what you expected. Second experiment: /sys/devices/system/clocksource/clocksource0/available_clocksource listed xen, tsc, hpet, acpi_pm; current was xen, matching the pvclock_clocksource_read() frame in the flame graph. Echoing tsc into current_clocksource took effect immediately: TimeBench then ran real 0m3.370s, user 0m3.353s, sys 0m0.026s, over 20x faster than before and nearly 4x faster than CentOS. At roughly 33 ns per call the loop instructions themselves inflate the number; partially unrolling the loop would tighten it. TSC reads time with a single RDTSC instruction and works through vDSO with no syscall. TSC was historically avoided over clock-drift concerns; a processor engineer met at a conference said tsc had been stable for years but knew of no public reference. Combined with Netflix's fault-tolerant cloud, that was enough to try tsc in production. Production graphs showed write latencies drop 43%, slightly better than CentOS, and os::javaTimeMillis() fell to 1.6% with only a vdso frame above it.
