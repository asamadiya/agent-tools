Raw material for a design-details subsection of the in-place pod resize KEP, covering how the kubelet actuates a resize and what happens when a memory limit goes down. The resources the kubelet asks for are not necessarily what the container ends up running with: the Linux kernel enforces minimums on CPU shares and quota, the systemd cgroup driver rounds CPU quota up to the nearest 10ms, and NRI plugins can rewrite the configuration. So a level-triggered comparison of desired against actual cannot decide whether a resize is needed. The kubelet therefore keeps a per-container set of 'actuated' resources: the configuration it handed to the runtime via CreateContainer or UpdateContainerResources and got a success back for. Actuated resources are checkpointed next to allocated resources so they survive a restart; because a badly timed restart can repeat a request, UpdateContainerResources must be idempotent. After a successful CRI resize the pod is marked for resync; if actual does not match desired, that shows up in pod status but is not otherwise acted on. A failed resize is retried on every subsequent pod sync until it succeeds or the container terminates. Lowering a memory limit below current usage: with cgroups v1 the kernel rejects it, with cgroups v2 it triggers an oom-kill. With resize restart policy NotRequired the kubelet reads container memory usage via the StatsProvider and skips the resize for that container when usage exceeds the desired limit; PodResizeInProgress stays with reason Error and a message giving usage and desired limit. This is best-effort: a TOCTOU race remains. The same check runs at pod level before lowering the pod cgroup memory limit. Nodes at v1.33 and earlier check only pod-level usage.
