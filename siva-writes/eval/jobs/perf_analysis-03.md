Netflix case study, later summarized at Kernel Recipes 2017. A microservice team doing metrics ingestion updated their base OS image (BaseAMI) and then claimed ZFS was eating over 30% of CPU capacity. The engineer asked to help had worked on ZFS internals at Sun Microsystems and did not believe it: unless badly misconfigured, ZFS cannot consume that much CPU. He checked anyway. Atlas, the cloud-wide monitoring tool, showed 38% of CPU time in sys, highly unusual for Netflix cloud workloads. Rather than SSH in for mpstat(1) and perf(1), he used Netflix's flame graph fetch tooling (Vector, later FlameCommander). The flame graph showed two orange kernel towers, left and right. The left tower was arc_reclaim_thread; the right entered spl_kmem_cache_reap_now(), another ZFS memory-freeing path, probably contending on the same locks. Background: the ZFS Adaptive Replacement Cache (ARC) is the filesystem's main memory cache; arc_reclaim_thread runs arc_adjust() to evict and to maintain a free-memory threshold, periodically or when woken by low memory. A known past cause of arc_reclaim_thread CPU burn was a tiny record size such as 512 bytes creating millions of buffers, but the default is 128 Kbytes and nobody should tune below 8 Kbytes. First theory: a new infrastructure project using ZFS for containers, churning containers and therefore filesystems. The team said they were not using containers, then said they were not using ZFS at all. df -h, mount and zfs list showed no ZFS filesystems mounted, on two instances. /proc/spl/kstat/zfs/arcstats showed every counter at zero: hits 0, misses 0, all of them. Root cause found by reading source and change history: a multilist performance feature had split ARC lists one-per-CPU to cut lock contention, and eviction picked a list at random using a cryptographically-secure random number generator; the flame graph paths led to get_random_bytes() and extract_entropy(). ARC was detecting low system memory, randomly selecting a zero-sized list at expensive cost, then finding nothing to do. Filed as ZFS issue #6531; the first fix had arc_reclaim_thread bail out earlier when ZFS was unused. Write the case-study narrative for an engineering blog read by systems and performance engineers.
