Raw material for the motivation and goals section of a Kubernetes enhancement proposal on pod scheduling readiness. Today a pod is treated as ready for scheduling the moment it is created, and the scheduler keeps trying to place every pending pod. In practice some pods sit for long stretches missing an essential resource, and the repeated attempts churn the scheduler and the downstream integrators that watch it, such as Cluster Autoscaler. Without a way to flag a pod as paused, those cycles are spent retrying pods already known to be unschedulable, which delays other pods and lowers overall scheduling throughput; it also constrains vendors who want to build features such as hierarchical quota natively. A constraint on any solution: the condition {type:PodScheduled, reason:Unschedulable} is the canonical signal the scheduler publishes so integrators such as Cluster Autoscaler know to add cluster resources, and that contract must not break. What the proposal wants: an API to mark pods scheduling-paused or scheduling-ready; a new Enqueue extension point so queueing behavior can be customized; paused pods must not be marked Unschedulable through the PodScheduled condition; and a default enqueue plugin that honors the new API's semantics. Out of scope: forcing pod conditions to expose more context about paused pods, and focusing on in-house uses of the Enqueue extension point. Noted as future work: permission control on individual scheduling gates, which depends on a fine-grained permissions design.
