Raw material for the constraints-and-caveats section of the pod scheduling readiness KEP, about the new .spec.schedulingGates field. State transitions are deliberately restricted. The field can only be initialized when the pod is created, either by the client or by a mutating admission webhook. After creation, gates may be removed in any order, but adding a new gate is not allowed. A scheduled pod must always carry empty scheduling gates, which means a client — administrator or custom controller — cannot create a pod that has schedulingGates populated and also specifies spec.nodeName; the API server returns a validation error. Stated as a matrix: for an unscheduled pod with nil nodeName, create with non-nil gates is allowed and update is not, while nil gates allow both; for a scheduled pod with non-nil nodeName, neither create nor update with non-nil gates is allowed, and nil gates allow both. Feature-gating is not uniform across the three parts of the feature: (a) the pod spec field plus feature gate and associated bits, (b) the SchedulingGates scheduler plugin, and (c) the underlying scheduler framework change, the new PreEnqueue extension point. Disabling the feature turns off a and b but leaves c on, so a plugin developer can use c alone to build their own equivalents of a and b. Separately, kubectl gets a new phase literal, SchedulingPaused, in the phase column of kubectl get pod, to show whether a pod is scheduling-paused.
