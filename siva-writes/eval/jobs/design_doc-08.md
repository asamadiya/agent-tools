Raw material. The feedback loop hypothesis: in the long term, coding agents will find tasks with effective feedback easy and tasks without effective feedback hard, and the availability of accurate feedback sets the limit on their capability. Current evidence. Good error messages keep agents unstuck. Rust steers agents toward correct code by signalling some kinds of incorrectness explicitly and immediately. Agents do well on performance work where good benchmarks exist. Property-based testing is unusually valuable. Agents do poorly on architecture, where feedback is of the know-it-when-I-see-it kind, and on concurrent programs, where feedback arrives as silent data corruption at runtime. Two comparison problems: building a delightful, ergonomic photo-editing website, and building a correct high-performance database storage engine at the scale of RocksDB or InnoDB, not Aurora DSQL or PostgreSQL. For open-loop models the website is easier and gets closer to success in a single shot. The hypothesis inverts this over the long run: the website's loop needs a human, and humans are slow, squishy, inconsistent feedback providers, while the storage engine has a simple specification covering API, safety properties, and liveness properties, so iteration needs no human. Implied tooling: Rust, Hydro, Verus at compile time; TLA+ and P at modelling time; Kiro's spec analyzer; testing tools, simulators, mocks. Write a design doc for engineering leadership on where to invest in agent tooling.
