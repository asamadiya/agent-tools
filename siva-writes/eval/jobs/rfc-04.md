Raw material for the motivation and scope section of a Kubernetes enhancement proposal on node memory swap support. Two constituencies want swap, and they overlap: node administrators tuning node-level performance and stability and reducing noisy-neighbour effects, and application developers whose programs benefit from swap memory. Three scenarios describe how swap could be used on a node: (1) swap enabled on the host but the kubelet does not let Kubernetes workloads touch it; (2) swap enabled at node level, with the kubelet permitting workloads scheduled there to use some configured quantity; (3) swap set per workload, with the kubelet setting a limit for each one. Scenario 1 is a prerequisite for the rest. This proposal covers 1 and 2 only; 3 goes to a follow-up KEP, and the enablement work here is what that follow-up needs. Goals: on Linux, kubelet can start when swap is provisioned and available; a configuration knob sets how much swap is available to workloads, defaulting to zero; cluster administrators configure this per node; swap works with cgroups v2. Non-goals: non-Linux operating systems, provisioning the swap itself, setting swappiness (already settable system-wide), per-workload allocation with accounting or APIs for customizing how limits are computed (so swap is an overcommitted resource here), zram, zswap, SGX EPC, cgroups v1, pod-level swap API, scheduling that targets swap-enabled nodes, and making the eviction manager swap-aware — the existing QoS-tier eviction hierarchy is kept as is.
