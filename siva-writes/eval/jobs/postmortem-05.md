Raw material: remediation plan following Cloudflare's 20 February 2026 BYOIP prefix-withdrawal outage, where a cleanup sub-task passed pending_delete with no value and deleted roughly 1,100 prefixes and their service bindings. Three workstreams. First, API schema standardization: pending_delete was passed as an untyped string, so neither client nor server could reason about its value; a stricter schema lets tooling validate whether a call is well formed. Second, separating operational state from configured state. Today customer configuration and operational actions hit the same authoritative database, which forces engineers to recover from database snapshots rather than reconcile desired against actual state. The plan is to snapshot what is read from the database and applied to production, then roll those snapshots out the same way binaries ship, gated by health metrics that halt a bad rollout, giving near-instant revert of individual customers or all customers to a known-good version. The stated tradeoff: during an outage customers are temporarily blocked from direct API updates, but their traffic keeps being served instead of going down. Third, a circuit breaker: monitoring that flags an unusual rate or breadth of change, for instance a burst of BGP prefix withdrawals or deletions, and halts snapshot deployment; signals from direct monitoring of customer services can also trip it. Recovery classes observed: withdrawn only, recoverable by dashboard toggle; withdrawn plus some bindings removed, partially recoverable; withdrawn plus all bindings removed, needing a global config push to every edge machine. All of this sits under Code Orange: Fail Small, whose three buckets are controlled rollouts for any network-propagated configuration change, break-glass procedures without circular dependencies, and well-defined behaviour under all failure modes.
