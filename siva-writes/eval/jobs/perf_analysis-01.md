Netflix, 2014, migrating services from CentOS Linux to Ubuntu. A Cassandra database cluster moved to Ubuntu and write latency went up by over 30%; basic stats showed over 30% higher CPU consumption. Instances are EC2 Xen VMs. Steps and results: top(1) showed only the Cassandra database consuming CPU, no rogue Ubuntu service. execsnoop(8) (Ftrace version at the time) showed no short-lived processes. CPU flame graphs were collected on a CentOS instance and an Ubuntu instance in parallel so the time-of-day traffic mix matched. Java stacks were broken in both (pre -XX:+PreserveFramePointer era), only one or two green frames instead of a tower of Java methods. That breakage accidentally merged the os::javaTimeMillis() calls into one block instead of scattering them as thin stacks: 30.14% in the middle of the Ubuntu flame graph, 32.1% total after searching. os::javaTimeMillis calls gettimeofday(2), entering tracesys() and syscall_trace_enter/exit(). Two theories: (A) syscall tracing enabled on Ubuntu (auditing? apparmor?), (B) fetching time is slower on Ubuntu via a library or kernel/clocksource change. Frame widths favored A. Caveat: profile used perf(1) with software cpu-clock soft interrupts, not hardware NMI, because it is a Xen guest, so interrupts-disabled kernel paths and all hypervisor time are invisible. Ubuntu showed a vDSO frame with the syscall still above it, because Xen pvclock did not support vDSO then. Colleagues had not hit it and the internet had nothing on os::javaTimeMillis, clocksource, tracesys, Ubuntu, EC2, Xen.
