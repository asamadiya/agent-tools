A 20-year history piece on frame pointers, written March 2024. Background the reader needs: %rbp is the x86-64 ABI's frame pointer, the register holding the base of the current stack frame, and external profilers and debuggers - Linux perf, eBPF - walk stacks by following it, which is what makes flame graphs possible. The ABI marks that use as optional: code can index into the frame off %rsp instead, which drops two instructions from each function's prologue and epilogue and hands back one general-purpose register.

2004: gcc developer Roger Sayle patched the i386 backend so that 32-bit targets compiled as though -fomit-frame-pointer -ffixed-ebp had been passed. On i386 that mattered: four general-purpose registers became five, or six to seven if you count %si and %di. Sayle gave two further reasons - he wanted to beat Intel's icc on benchmarks, and he took the view that debuggers of the day would be unharmed, since they supported other ways of walking a stack.

The extension: the same default was carried across to x86-64, a target that already had more than a dozen registers and so gained very little from one more. Eric Schrock, then at Sun, objected in November 2004. On amd64, he wrote, a 17th general-purpose register opens up no new class of compiler optimization; all you avoid is a pushl/movl sequence that the hardware has long since optimized; leaf routines never establish a frame at all; and set against the cost in lost debuggability the trade hardly seemed worth making. His closing line: the practice goes off the rails once people begin compiling /usr/bin without frame pointers. Linux then did exactly that, and not only /usr/bin - /usr/lib and application code too.

What it costs in practice: a stack walk terminates when it reaches libc, so the trace comes back without its application frames, and those truncated stacks pile up together on the left edge of a flame graph - 15% of the samples in one example. Off-CPU flame graphs come off worse still, since libc read/write and mutex calls are most of what they contain.

2014, joining Netflix: Java had no frame pointer support, which broke every application stack. The author wrote a c2 compiler fix for the JVM; Oracle reworked it and shipped it as -XX:+PreserveFramePointer in JDK8u60. libc came next - he built his own with frame pointers for production, then worked with Canonical on a prebuilt libc6-prof.
